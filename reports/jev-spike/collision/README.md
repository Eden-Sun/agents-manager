### 校準

把 Score 的 `P(level≥2)` 當撞題機率：`brier=0.080`，分佈幾乎是兩極的——

| P(level≥2) | n | 實際撞題 |
|---|---|---|
| < 0.2 | 23 | 0.09 |
| 0.2–0.8 | 8 | 0.00 |
| ≥ 0.8 | 17 | 0.94 |

Noul 同樣乾淨：p<0.4 的 30 筆只有 2 筆是真（就是下面那兩題漏的）；
p≥0.6 的 13 筆全部是真。**高分可信、低分大致可信，中間帶幾乎沒有東西**，
所以門檻放哪裡不太敏感（0.4 與 0.5 只差一筆）。

### 兩題漏的都是同一件事

`354-vs-296`（noul 0.17）、`354-vs-284`（noul 0.11）。這是票上明寫要測的那一類
——**不同檔、同一個根因**：`#355` 設計提案點名 `#248 #284 #296 #353 #354`
是「多步驟中途留半套、開機後沒有持久紀錄可接續」的同一族，該用一個共用機制解。
Jev 看兩張票的文字時看到的是「delete_project 的 child 軟刪失敗 early return」
與「重啟時 daemon 行程死在 stop 與 start 之間」——**觸發條件確實不同**
（一個是回錯、一個是行程死亡），只有把兩者放進「先 commit 的那一步留半套」
這個架構角度才是同一件事。那個連結是後來人做架構 review 才建立的（#355），
不在任何一張票自己的文字裡。

**這是這次最重要的限制**：Jev 抓得到「這兩張票在講同一個機制」，
抓不到「這兩張票屬於同一個需要重新設計的家族」。後者仍然要人。

## 確定性路徑比對在哪裡仍然比較好

票面提到同一個原始檔當成唯一判斷：precision 0.57、recall 0.22。
18 個正例裡它只抓到 4 個，Jev 在它漏掉的 14 個裡抓到 12 個。所以**不能用路徑比對取代**。

但它抓到的三個「誤報」——`208-vs-199`、`251-vs-249`、`312-vs-308`——
語意上我標 1（同一個檔、不同的 bug）是對的，**Jev 也正確地把它們壓在門檻之下**。
這三對放進現實會怎樣？兩顆 agent 同時改 `stop.rs` / `watchdog.rs` / 同一支 kick 腳本，
**git 上會衝突**，跟它們是不是同一個 bug 無關。

結論是兩個訊號問的是不同的問題，不要合併成一個分數：

- `ownership_conflicts()` 的路徑比對回答「**會不會改到同一個檔**」——
  免費、同步、不會錯，是併版風險；
- Jev 回答「**是不是同一個問題**」——要 0.3 秒、要錢、會錯，是重工風險。

兩個都要，而且提示文字要分開寫，不要讓使用者以為「同檔」就是「重複票」。

## 建議：值不值得接、接在哪

**值得接，但只接 Noul、只當提示、而且要接在兩個地方。**

1. **用 `same_work` 這條 Noul 當旗標，門檻 0.5**（precision 0.94 / recall 0.89 / 誤報率 0.03）。
   Score 不要拿來做是非判斷（同樣的 recall 下誤報率是三倍），
   但**可以拿來排序已經被旗標挑出來的那幾張**（top-1 0.88）。
   這跟 #240 的結論一致：窄的 Noul 可靠，多選一／量表不可靠。

2. **接在兩個入口，都是 shadow／只記錄：**
   - **開票前**：`release-triage` 與 AGM 巡檢要開新 issue 時，
     拿候選對同專案「開著的」票各問一次（目前 15 張），把 ≥0.5 的寫進帳本並在票上留一句
     「可能與 #N 重疊」。**不可以擋住開票**（票上的非目標）。
   - **派工前**：`supervisor::assign` 在現有 `ownership_conflicts()` 路徑比對**之後**，
     對「在飛的交辦」再問一次，結果推 AGM 收件匣當提示。同樣不取消交辦、不決定 ownership。
   - 兩者共用 #240 已經做好的 `[judge]` 開關、專案名單、`max_per_hour` 保險絲與
     `judge_shadow` 帳本（`daemon/src/judge.rs`，SPEC §4.3c），不要另開一套。

3. **外送內容比既有兩個場景乾淨**：送的是 issue 標題與前 450 字，
   都已經在 GitHub 上；不送畫面、不送對話、不送原始碼。
   遮罩需求因此比撞限第二意見低，但**交辦的 text 是使用者寫的**，
   派工前那一路仍要走現有的遮罩。

4. **現實的誤報率會比表上差**。這批樣本每個候選 5 個對照、正例佔 37.5%，
   現實是 15 張開票裡通常最多 1 張真的撞題（基準率約 7%）。
   用量到的 recall 0.89 與誤報率 0.03 推：每張新票期望 0.89 個真提示＋0.42 個假提示，
   **precision 掉到約 0.68**——大約每三則提示有一則是雜訊。
   當提示可以接受，當自動合併不行。

5. **先記一段時間再談要不要顯示**。對帳標籤是現成的：提示出現後那張票最後有沒有
   被關成重複／被連結／被併進另一張。累積 ≥20 則真的提示再決定要不要從帳本升級成
   票上留言。若一段時間內 `judge_shadow` 根本沒有撞題列，那也是結論
   （代表現有的路徑比對＋人看已經夠）。

**不建議做的**：拿 Score 當自動門檻、拿它排序全部 405 張票（成本與誤報都會爆）、
或期待它找出「同一個根因族」這種要架構視角的重複——那是 #354 那兩題漏掉的原因，
只能靠人做設計 review。
