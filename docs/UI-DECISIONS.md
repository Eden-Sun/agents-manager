# UI 優化決策清單（Codex gpt-5.6-sol，依 2026-09-06 實機截圖 200–204）

> 決策者：Codex sol；實作者：Grok；輸入截圖：`docs/screenshots/200-v40-chat-dark.png` … `204-v40-settings-dark.png`。

### [優先級 P0] 群組聊天必須明確指定收件者與發言者

- 現況問題：202 中使用者訊息只有氣泡下方的小字 `→ @am-claude` 表示收件者；agent 名稱也放在回覆氣泡下方。快速掃讀時難以立即判斷「誰對誰說話」。輸入框只靠 `@bot 或 @all…` placeholder，容易漏填或誤送給全部 bot。
- 決策：在群組 `.composer` 上方加入 36px 高的收件者列，包含 `@all` 與各 bot chip，間距 8px；未選收件者時停用送出。選擇器只負責產生既有 `@bot` 語法，不改協定。`@all` 使用警示色並顯示「3 個 bot」。每則訊息在氣泡上方放 18px 高 metadata：左側為 `am-claude · Claude` 或 `你 → am-claude`（13px/600），右側為時間（11px）。Claude、Codex、Grok 分別使用琥珀、藍、石墨色的 3px 標記，但名稱文字必須同時存在，不能只靠顏色辨認。
- 驗收方式：隨機查看連續 10 則群組訊息，1 秒內可說出發言者與收件者；未選對象無法送出；選 `@all` 時畫面明確顯示實際收件 bot 數量。

### [優先級 P0] 降低停止、刪除錯誤操作風險

- 現況問題：200–205 的每個運行中 bot row 都固定顯示紅框「停止」，頂欄又重複一個；大量紅色搶過名稱、模型及狀態，且容易停止錯誤 bot。204 的刪除操作同樣缺少足夠的對象確認。
- 決策：側欄 bot row 不再常駐紅色停止按鈕，改為尾端 32×32px 操作選單，僅在選取、hover 或鍵盤 focus 時出現；「停止」移入選單。當前 bot 頂欄保留一個 64×32px「停止」，點擊後以 360px 寬確認框顯示 bot 與 project 全名。「中斷」維持一鍵操作但使用中性色。刪除 Bot 必須輸入 bot 名稱後才能確認。紅色只出現在確認階段、危險區及 hover，不作為常態列表色。
- 驗收方式：一般聊天畫面最多只有一個常駐危險操作；任何停止或刪除確認都能看到完整 bot/project 名稱；按 Escape 或「取消」不會改變程序狀態。

### [優先級 P1] 收斂主要版面寬度與閱讀動線

- 現況問題：在 2048px 截圖中側欄約 421px，訊息左右端相距超過 1400px；長回覆行寬過長，短對話又形成大量無意義留白。
- 決策：側欄寬度設為 `288–344px`，桌面預設約畫面寬度的 18%；聊天區建立置中的 1180px 最大寬度 conversation lane。agent 氣泡最大 840px，使用者氣泡最大 640px，且皆不得超過 lane 的 78%。頂欄高 56px、composer 高 76px；訊息區水平 padding 24px、同一發言者訊息間距 12px、不同回合間距 24px。視窗低於 1024px 時側欄改為可開關的 overlay。
- 驗收方式：在 1280、1440、2048px 寬度下皆無水平捲動；一般中文段落每行約 35–50 字；左右對話不需大幅轉動視線即可追蹤。

### [優先級 P1] 精簡側欄資訊層級

- 現況問題：專案路徑即使在 421px 側欄仍被截斷；每個 bot 同時呈現 lamp、kind、model、identity、齒輪與停止按鈕。底部的新增、主機、身分與 kind 顯示設定又與主要清單競爭注意力。
- 決策：project header 高 48px，第一行顯示專案名稱，第二行以 11px 顯示截斷路徑；完整路徑由 tooltip 提供。bot row 高 52px：第一行為 8px lamp、14px/600 名稱與狀態；第二行最多顯示兩個 20px 高 metadata badge，其餘放入詳情。project 操作 icon 只在 selected/hover/focus 顯示，點擊區至少 32×32px。底部只保留兩個 36px 高的「新增 Project／新增 Bot」，主機、身分、kind 顯示合併至「環境設定」disclosure。
- 驗收方式：側欄同時顯示 8 個 bot 時仍能快速掃讀名稱與運行狀態；沒有一列因控制項擠壓而看不到 bot 名稱；完整路徑始終可查。

### [優先級 P1] 將缺少 CLI 提示改為情境式警示

- 現況問題：200–205 中「有主機缺少 agent CLI」區塊約佔 140px 高，即使目前正在使用 Claude、缺少的是 Grok，仍持續壓縮所有聊天及設定畫面；灰色 summary 又不像警示，藍色安裝按鈕反而最搶眼。
- 決策：只有當目前 bot 或群組收件者受到影響時，才在頂欄下方顯示 44px 高警示列；內容為 13px 文字、32px 高次要按鈕與展開箭頭。無關當前工作時，縮成頂欄的琥珀色狀態圖示及數量。摘要採「m4p 缺少 Grok CLI」，多筆時顯示「1 台主機缺少 2 個 CLI」；詳細清單展開後最大高度 160px。
- 驗收方式：進入未受影響的 Claude 對話時不再出現大型警示；受影響 bot 的訊息區頂端仍不低於畫面 y=120px；從摘要可直接知道主機及缺少的 kind。

### [優先級 P1] 把額度資訊拆成可辨識的 kind 單元

- 現況問題：頂欄目前把多組 `5h 剩…／7d 剩…` 串在同一行，主要依靠小圖示區分 kind；202 又同時存在群組成員 chip，資訊容易黏在一起。`1%` 與 `98%` 的風險層級也不夠明顯。
- 決策：每個 kind 使用獨立 132×40px quota pill，左側顯示 16px icon 與 12px kind 名稱，右側上下排列 `5h 1%`、`7d 77%`（11px）。剩餘量低於 10% 使用紅色、10–29% 使用琥珀色、30%以上使用一般文字加綠色進度標記；百分比始終保留，不能只用色彩。畫面寬度低於 1600px 時只顯示目前 kind 或最低額度 kind，其餘收入「全部額度」popover；無資料明確顯示「無資料」，不只放破折號。
- 驗收方式：使用者在 2 秒內能指出「哪個 kind、哪個週期即將耗盡」；1280px 寬度下不與群組成員或停止按鈕重疊。

### [優先級 P1] 重建淺色主題的對比角色

- 現況問題：201 中 canvas、composer、停用控制項及訊息 metadata 都落在相近的淡灰色；時間、`hook` badge、路徑及未選狀態偏弱，選取中的側欄 row 也不夠明確。
- 決策：淺色使用 canvas `#EEF1F5`、surface `#FFFFFF`、subtle surface `#F6F8FA`、主文字 `#1B2430`、次文字 `#5E6A78`、邊框 `#C8D0DB`、primary `#2F6FE4`；選取列用 `#E6EEFF` 加左側 3px primary。深色使用 canvas `#15191F`、surface `#1D222A`、raised surface `#262C35`、主文字 `#F1F4F8`、次文字 `#A8B2C0`、邊框 `#3C4653`。composer 必須是 surface，而非與 canvas 同色；重要文字不得靠低 opacity 製造弱化。
- 驗收方式：兩個主題的普通文字對比至少 4.5:1，控制項邊界與 focus ring 至少 3:1；100% 縮放下可直接讀出時間、來源 badge、路徑與停用原因。

### [優先級 P1] 統一訊息結構與輸出層級

- 現況問題：200/201 中時間與 `hook` 標記游離在氣泡下方；短回覆如 `1`、`V40-OK` 的容器比例不一致；一般 agent 回覆、hook 輸出及程式碼主要依背景深淺區分。
- 決策：所有訊息固定為「18px metadata row＋4px 間距＋bubble」。bubble 不設最小寬度，最小高度 36px，padding 為上下 10px、左右 14px，圓角 14px；正文 15px/24px，程式碼 13px/20px。agent 使用中性 surface＋1px border，使用者使用 primary；hook／系統輸出增加 3px 中性左側 rail 與 monospace source badge，不使用一般 agent 樣式。訊息列表頂部與底部保留 16px scroll padding，避免首尾內容被裁切。
- 驗收方式：短回覆會貼合內容，不再形成不必要的大盒子；不閱讀文字也能分出使用者、agent 與系統輸出；長程式碼只在 code block 內水平捲動。

### [優先級 P1] 重排新增 Bot 表單並消除模糊預設值

- 現況問題：203 以 `foo-claude` 作為名稱提示，kind 預選 Claude、模型與身分都只寫「預設」，使用者無法知道實際會採用什麼；表單直接插入清單並把其他 bot 推到下方。
- 決策：新增流程在側欄內切換成暫時性 sheet，而不是插入清單；頂部顯示「新增 Bot · agents-manager」與返回按鈕。欄位順序固定為「kind → 模型 → 身分 → 名稱 → 人設」。kind 預設為該 project 最近使用且已安裝的 CLI；沒有紀錄時選第一個可用 CLI，未安裝者停用並標註原因。模型改寫為「使用 CLI 預設」，身分改寫為「不指定身分（本機預設）」。名稱預填唯一的 `{kind}-{序號}`，人設預設不設定並維持收合。欄位高 40px、垂直間距 16px；名稱無效或 CLI 不可用時停用「新增並啟動」。
- 驗收方式：畫面上不再出現無法解釋的「（預設）」；只用鍵盤即可依正確順序完成建立；任何可按下的建立操作都有有效名稱及可用 CLI。

### [優先級 P1] 將 Bot 設定改為固定寬度側面板

- 現況問題：204 的設定表單只占主內容左半部，右側留下大面積空白；不可修改的 kind 被做成 disabled input，容易被誤認為表單錯誤；關閉鈕與儲存鈕相距過遠。
- 決策：設定改為右側 520px drawer，可在 `440–560px` 間響應；低於 1180px 時才占滿主內容區。header 高 56px、body padding 24px、欄位間距 20px、sticky footer 高 72px。kind 移到標題旁作 read-only badge，不再做 disabled input；編輯順序為「名稱 → 模型 → 身分 → 人設」。未修改時停用儲存；有未儲存內容時關閉須確認。危險區與一般設定間隔 32px，刪除確認在區塊內展開。
- 驗收方式：204 尺寸下不再出現超過 560px 的無效表單寬度；關閉後回到原聊天捲動位置；修改尚未儲存時不會因誤按關閉而遺失。

### [優先級 P2] 為無 bot、無訊息與停止狀態提供不同空狀態

- 現況問題：現有畫面在訊息少時只剩大片空白；未運行的 Grok 只以空心 lamp 和「啟動」表示，缺少「現在能做什麼」的主內容引導。
- 決策：空狀態最大寬度 360px，置中於 conversation lane；icon 40px、標題 16px/600、說明 13px/20px、元素間距 12px。無 bot 顯示「此專案尚無 Bot」及 40px 高新增按鈕；無訊息顯示「開始交代第一個任務」並自動 focus composer；bot 已停止時保留歷史，在 composer 上方顯示 48px 狀態列與「啟動」按鈕，composer 停用並說明原因；daemon 斷線則顯示全域連線狀態，不偽裝成 bot 空狀態。
- 驗收方式：首次進入每一種狀態時，測試者在 5 秒內能指出下一個可執行動作；停止狀態仍可閱讀歷史，但無法誤以為訊息已送出。

### [優先級 P2] 統一 icon、tab 與鍵盤操作規格

- 現況問題：project header 的終端、加號、關閉與 bot 齒輪都很小且缺少文字；203 中藍色加號只靠狀態色表達用途，鍵盤 focus 也不明顯。
- 決策：頂欄及 project 操作點擊區統一為 36×36px，bot row 內最小 32×32px；`.tab` 高 36px、左右 padding 14px。所有無文字 icon 在 hover 400ms 後顯示動作名稱及作用對象。鍵盤 focus 使用 2px `#76A7FF`、offset 2px；hover、selected、focus 必須是三種可區分狀態。
- 驗收方式：只使用 Tab、Enter、Space、Escape 可完成切換聊天/終端、開啟設定、新增 Bot 與取消操作；每個 icon 都有可見 tooltip，focus 不會被背景或裁切隱藏。

### 不要改什麼

保留「左側依 project 分組、右側聊天」的核心模型；保留使用者靠右、agent 靠左的對話方向；保留 lamp 對運行狀態的即時提示、kind/identity badge 的緊湊語彙、聊天/終端 tab，以及設定頁已獨立出的危險區。不要改成卡片牆、三欄 dashboard 或為每個 kind 填滿整個訊息背景；kind 色彩應繼續只作辨識標記。所有調整都應保留既有指定 class 契約。

## 2026-09-07 圖片暫存托盤（新增取捨）

- **右緣一條可收合窄欄，而不是右下角浮動托盤。** 浮動托盤會蓋住訊息與輸入框，而這個區域
  是「常駐」的（不屬於任何對話），一直懸在內容上方比缺點更明顯。窄欄是 `.app` grid 的
  第三格，收合 38px、展開 208px，關掉的偏好會記住。`≤1024px` 移到**底部**同樣是 grid 一格，
  不做 sheet：手機上 sheet 蓋掉的正好是輸入框。
- **點一下就放進目前對話，拖放只是桌機的加分項。** 觸控裝置沒有 HTML5 拖放，若只做拖放，
  手機就完全用不到這個功能。所以「點」是主要動線，兩個平台一致。
- **複製，不是搬移。** 圖片放進對話後仍留在暫存區——同一張截圖常常要餵好幾隻 bot，而誤觸
  也不該弄丟唯一的一份。移除是明確的動作（× 或清空），並在卡片上閃一下「已放入」當回饋。
- **暫存區不上傳，但會留 30 分鐘。** 附件 id 綁收件 bot 的 project，先上傳等於先賭一個對象；圖片
  放在暫存區期間只存在瀏覽器裡（`File` 鏡射到 IndexedDB，localStorage 裝不下 blob），直到它
  真的被丟進某個對話。重新整理不會消失；從放進去那一刻起 30 分鐘後自動清掉（載入時與每分鐘
  各檢查一次），不是「最後一次用」起算——這是暫存不是圖庫（2026-09-08 改，原本是重整就沒）。
- **放大預覽固定在托盤外緣，不跟著游標。** 跟著游標的預覽會抖，而且一定會經過卡片與它的
  移除鍵；固定在窄欄左側（底部托盤時在整條之上）位置可預測，也是唯一能保證「不擋移除鍵」
  的做法——只避開卡片還是會壓到標題列的 ＋ / ✕ / »。預覽一律 `pointer-events: none`。
- **觸控用長按開預覽，不用「點一下」。** 點一下已經是「放進對話」，那是手機上唯一的主要
  動線，不能拿去換預覽；長按開、再點一下收。桌機 hover 有 180ms 延遲，focus 立即（鍵盤
  使用者要的是資訊，不是防手滑）。
- **預覽一律撐到對話框那麼寬（2026-09-08 改，原本固定 300px）。** 300px 的預覽還是只能
  「看出是張截圖」，認不出是哪一張，等於白開一個浮窗；改成量 `.chat` 的寬度，高度仍由
  上／左方真正剩下的空間（`--peek-avail`）夾住。圖只放大到自己的原尺寸為止——小圖撐滿只
  會糊。輸入框上方那排待送出的縮圖（`.attach-tray`）同理：hover / focus 在托盤正上方浮一張
  滿版預覽（`position:absolute`，版面一格都不動），離開就收。
- 上面「不要改什麼」那條（保留左側 project 分組、右側聊天的核心模型）不受影響：暫存區是
  版面外緣的一條 utility 欄，不是第三個內容欄，空的時候只有標題列與一行說明。

## 2026-09-07 「這回合的提問」浮窗（新增取捨）

- **浮窗，不是版面裡的一列。** 它只在回合進行中存在；若讓它佔掉高度，每個回合的開始與
  結束都會把整串訊息上下推一次。浮在 `.msg-list` 上緣（`.lastq-slot`，`position:absolute`）
  只蓋住捲軸最上緣那一段——那裡通常是已經讀過的舊訊息，而視線在等待時是盯著底部的。
  代價是它確實蓋住東西：所以底色不透明（半透明會讓兩層字疊在一起）、有關閉鍵，
  而且只在「有進行中的回合」時出現。
- **釘下緣（2026-09-08 改）。** 原本釘上緣，理由是下緣是「↓ 最新」與 composer 的地盤、
  提問只是參照。使用者實際用起來要的是「提問跟正在冒出來的輸出在同一個地方」——等待時視線
  盯著底部，釘在上緣得抬頭找。改成貼著 `.msg-list-wrap` 下緣（`bottom:0`），會蓋住最新輸出
  的最後幾行與「↓ 最新」的左側；有關閉鍵，看完就收。
- **夾三行（手機兩行），不是一行摘要也不是全文。** 一行截斷認不出是哪一題；全文則會讓一段
  長規格蓋掉半個對話區。三行足夠辨認，其餘交給展開。展開後給 `40vh`（手機 34vh）上限並
  自己捲，超長提問不會因為「展開」就吃掉整個畫面。
- **兩段點擊：展開 → 捲到那則。** 「展開」與「捲過去」都是這個浮窗該有的動作，但塞兩顆按鈕
  在一張 60px 高的卡片上太擠，而且對觸控來說整張卡當點擊區才好按。所以同一個點擊區分兩段，
  右上角用一句話說明下一段會做什麼（`點一下 · 展開全文` → `再點一下 · 捲到這則`）。
  短到沒被夾的提問沒有第一段，一點就直接捲過去——沒有東西可展開時不該假裝有。
  捲過去之後收回夾行狀態：人已經被送到訊息本身了，浮窗不必再佔三行以上。
- **捲過去要閃一下。** 停在一堆長得一樣的氣泡中間，不閃就不知道停在哪。用 `.msg.flash`
  在氣泡外圍打 1.6 秒的 accent 光暈；連按兩次時先把 class 拿掉再掛回去，動畫才會重播。
  這也是 `Bubble` 開始帶 `data-msg-id` 的原因——那是目前唯一能從清單外面指回某一則訊息的把手。
- **關閉只管這一回合。** 關掉的是「這一題我已經記得了」，不是「以後都不要」；下一個回合是
  另一題，值得再問一次（跟 `BlockedModal` 的 `dismissed` 同一個道理）。狀態綁在 turn id 上，
  換回合自動回到「夾行、沒關過」。
- **內容優先取這個回合自己的 user 訊息**，沒有（bot / team 起頭的回合）才退回整串最後一則。
  退回的那則仍然是「使用者最後說的話」，比什麼都不顯示有用。

## 2026-09-07 主機 shell（新增取捨）

- **主面板的一頁，不是 modal。** 這件事的動線是「開著它、一邊看輸出一邊下下一個指令」，而
  modal 蓋掉的正好是你想同時看的東西（側欄的主機清單、剛才那個 bot 的狀態）。所以它跟
  `TeamLaunchPanel` 一樣是主面板的一個分支，`shellView` 與 `selectedBotId` /
  `selectedProjectId` / `selectedTeamId` / `teamLaunch` 互斥，而且**排在最前面**：那是使用者
  剛剛按出來的視圖，比背景那個選取更該被看到。
- **入口留在「環境設定 → 主機」的每一列，按完就把彈窗收掉。** 開 shell 是「對這台主機做
  一件事」，跟重連、看 CLI 徽章、gh 登入是同一組動作，放在同一列最好找。但那張清單本身
  在彈窗裡，不收掉的話按完什麼都沒發生——新面板正好被蓋在後面。用的是 `Modal` 自己記載的
  關閉路徑（Escape），而不是另拉一條 store 狀態：彈窗的開關是 `Sidebar` 的本地狀態，
  模擬它自己的關閉動作才不會兩邊對不上。失敗時彈窗留著（原因與「重連」都在那一頁）。
- **按第二次「開 shell」是接回剛剛那個，不是再開一個。** 一台主機通常只需要一個 shell，
  而回來時想看的是上一個指令的輸出，不是一片空白。要「在某個目錄另開一個」才明確帶 `cwd`。
- **一行輸入 + 一排按鍵，不做整頁鍵盤接管。** `BlockedModal` 把每一顆鍵都轉給 pane，那是
  因為那裡在回答 TUI 的問題；shell 的主要動線是「打一行、按 Enter」，↑↓ 讓給指令歷史比讓
  給 pane 有用得多（那是這個面板唯一記得住的東西），Tab 也得留給瀏覽器走焦點。真的要按
  整片鍵盤的情境，按鍵列上的 `ctrl+c` / `Esc` / `Tab` / `↑` / `Enter` 就夠。
- **「清畫面」是真的送 `clear`，不是前端清 state。** 使用者要的是終端乾淨；把畫面上的字
  清掉只會在下一次輪詢（1 秒後）全部長回來，那比不做更糟。
- **兩種讀法，預設「畫面」。** `visible` 是「終端現在長什麼樣」，這是 shell 的常態；另一顆
  切到 `recent_unwrapped` ＋ 行數選單，看已經捲上去的輸出。herdr 對還沒捲過的 pane 這兩種
  `recent` 都回空字串（實測 2026-09-07），所以空的時候要**明講**「還沒有捲出畫面的內容」——
  一片空白看起來就是壞掉。
- **不記在 localStorage 的選取記憶裡。** `pane_id` 活不過 daemon 重啟，記住它只會在下次
  開啟時指向一個不存在的 shell。指令歷史記（每台主機一份、20 筆），那個換 daemon 也還有用。
- **「關閉」與「結束 shell」是兩顆。** 關閉只收畫面、shell 留著（回來接得回去）；結束才關
  pane，而且要二次確認——裡面可能正跑著東西，而畫面上的輸出關掉就沒了。

## 2026-09-07 已完成（未讀）（新增取捨）

回合的狀態多一段中間值：**進行中 → 已完成（未讀）→ 已完成（已讀）**。實作在
`web/src/store/unread.ts`（純函式 ＋ localStorage），store 只掛最小的 hook。

- **「完成」不等於「看到了」。** 一個 agent 跑完 8 分鐘的任務時，使用者八成正在看別的 bot、
  切到別的分頁、或人根本不在電腦前。舊的模型裡那一刻就直接變成「閒置」，燈號從黃轉綠，
  然後**什麼都不留下**——回來的人只看到一排綠燈，得一個一個點進去才知道誰講過話。中間這
  一段就是為了那個人留的。
- **「在看」是三件事同時成立：選的是它、分頁可見、視窗有 focus。** 少了最後一項，把瀏覽器
  丟在旁邊那台螢幕、人在別的 app 打字時進來的回覆會被當成已讀——那正是最需要留著徽章的
  情境。反過來，視窗回到前景時要主動把「現在開著的那個」標成已讀（`visibilitychange` /
  `focus`）：不然人就坐在畫面前面看著訊息，徽章卻還亮著，清除的時機永遠不會到。
- **燈號和徽章是兩件事，所以是兩個記號。** 燈號說的是**現在**在做什麼（working / idle /
  blocked），徽章說的是**你還沒看過**幾個回合。把未讀塞進燈號的顏色會兩邊都說不清楚：
  一個閒置但有未讀的 bot，燈要綠還是要亮？所以徽章是獨立的一顆，並排在燈號右邊，而且是
  **方角小標而不是圓丸**——同一列裡兩個圓點會被讀成兩顆燈。
- **`!` 前綴不是裝飾。** 側欄很窄，數字被截斷、被誤讀成模型參數（`4`、`5`）都發生過。
  `!2` 在任何寬度下都只可能是一件事。顏色用 accent（跟群組未讀同一家），不用 danger：
  未讀不是錯誤，只是還沒輪到你看。
- **數字是「回合」不是「訊息」。** 一個回合可能吐好幾則（續寫、工具輸出、hook）。使用者心裡
  的單位是「它回我幾次」，不是「資料庫多了幾列」。同一個 turn_id 只算一次；`message_added`
  與 `turn_updated`（終態）都算完成，去重表負責讓一個回合只跳一下。
- **專案收合就把底下的加總掛回標題。** 收合是「這一區我現在不想看」，不是「這一區的事我
  不想知道」。不加總的話，收合等於親手把徽章藏起來，那正好背叛了這個功能。
- **分頁標題的 `(N)` 只算 bot 那一邊。** 群組未讀跟 bot 未讀是**同一批回覆**的兩份帳
  （每則回覆同時記在它的 bot 和它專案的群組聊天上）；兩邊相加會把一則回覆數成兩個。
- **跨重整保留，但不動 daemon。** 未讀是「這個人看過什麼」，是瀏覽器這一端的事實，daemon
  不該知道，也沒有地方放。localStorage 存兩份：**已讀標記**（最後已讀的訊息 id + 時間，
  這是真相）和**數字**（快照）。只有標記的話重整後算不出數字——那時只有正在看的那個 bot
  會載入訊息，其他的一則都沒有；只有數字的話會跟真實訊息漂移。所以兩個都存，訊息真的載
  進來時再用標記重算一次校正。
- **刪掉的 bot 要把帳一起刪掉。** 不然 localStorage 只會長，而且那個數字會永遠加在分頁標題
  上——一個永遠點不掉的未讀。每次 `GET /api/state` 之後清一次。

## RAM 展開清單（2026-09-08）

左上角那格從一個數字變成點得開的清單（`MemPopover`，SPEC §15.2、`docs/API.md`）。

- **一個總數回答不了使用者真正的問題。** 「RAM 4.5G」只說了痛，沒說哪裡痛。本機底下十幾個
  `claude`，一半是自己開的 pane 或舊的 `--resume`，從那個數字看不出哪些能砍——所以那格必須
  展得開。
- **只列每棵子樹的最上層，不攤平。** 一個 `claude` 底下掛著幾十個 node worker 與短命 helper；
  全列出來就成了 Activity Monitor，而使用者要的是「砍哪一個」。所以只列常見的 shell / CLI 且
  子樹 ≥ 8 MiB 的，其餘的位元組併進父程序。
- **排序與「大小」那一欄都用子樹加總，不是自己的 RSS。** 那一欄回答的是「砍掉能省多少」；
  只印自己的 RSS 會低估一個帶著三個 worker 的程序，使用者砍完發現沒省到。
- **bot 走「停止 bot」，不給 kill。** 直接送訊號只會留下一個 daemon 以為還活著的 bot：run 沒
  收、狀態沒更新。`POST /bots/{id}/stop` 才是那條會記帳的路，所以 bot 那幾列的按鈕就是它，
  daemon 端也把 `owner=bot` 的 kill 擋成 409。
- **TERM → 再按一次才 KILL。** TERM 讓 CLI 有機會把 session 寫完，第一次按通常就夠了；
  真的沒反應時那一列還在，按鈕已經換成紅色的「強制」。用兩段式而不是彈確認框：這是一列
  裡的一顆小鈕，為它開一個對話框太重，而「按鈕自己變樣」本身就是確認。
- **bot 那幾列淡一點。** 它們不是這張清單的重點；重點是可以砍的那些。
- **關著就不抓。** 一次取樣是一支 `ps`（遠端還是一趟 ssh）。打開時每 15 秒（daemon 的取樣
  間隔）重抓，關掉就停。
- **「自己開的 pane」點了開一個視窗，不在列底下攤開。** pane id 對人是亂碼；要知道「這是哪一個
  claude」只能看它畫面上的字。第一版在那一列底下攤開，560px 的清單塞不下 185 欄的終端，每行都
  折、還是認不出來——所以改成跟 `BlockedModal` 同寬的視窗（`MemPaneModal`），畫面幾乎原樣、
  每 2 秒重讀、捲到底。只讀，不給打字（要操作去 herdr 或終端分頁）。清單留在視窗後面不關，Esc
  只關視窗，看完回去按「結束」。bot 那幾列不給看——它們有自己的終端分頁，也不是要砍的對象。

## 2026-09-08 額度卡片可以「暫時停用」一個身分，它底下的 bot 先從側欄收起來

- **停用鍵長在額度那一格上，不在側欄 header。** 「額度快用完了，先別看到這些 bot」是對**某一組額度**
  下的判斷，不是對整份清單下的。所以每一格額度（`cc0` / `cc1` / `cc2` / `codex` / `grok`）自己帶一個
  勾選格；側欄不再有全域開關。
- **主要入口在條上那一格，貼在 kind 圖示／身分名的正下方。** 第一版只做在 popover 裡，實測時
  使用者找不到、也懶得先點開才切。第二版掛在整格下面自成一行，把條子從 52px 撐到 66px——標題列
  被吃掉一截。定案：開關進到左邊那一直欄（圖示、身分名、開關），右邊的量表高度不動。圖示欄
  （27px）本來就比三條量表（36px）矮，用負的 `margin-top` 把 10px 的方塊塞進那段空白，

- **codex／grok 的左欄補上 kind 名稱，三種 kind 用同一套結構。**（2026-09-08 補）`cc0`/`cc1`/`cc2`

  36px 之後比 grok 那條單獨的「週」量表（20px）高，**五格高度一律 44px**（實測
  `getBoundingClientRect`：cc0/cc1/cc2/codex/grok 全部 44），不會一高一矮。

  popover 裡那份留著當詳細版，有「停用／已停用」的字（窄視窗下條上只留焦點那一格，其餘從 popover 切）。
- **整格仍可點開 popover。** 頂端那條本來整個是一顆 `<button>`，checkbox 不能塞在 `<button>` 裡；

  checkbox／按鈕的點擊，不然會一次開一次關。
- **整格可點，停用態要看得出來。** popover 的卡片點本身等於切那顆 checkbox（從 checkbox 自己或登入鈕
  發出的點擊放行，不然會切兩次）。停用中的卡片降到 50% 透明並把名字劃掉；條上那一格同樣降透明＋
  劃掉身份標籤——不然得先點開 popover 才知道側欄少了誰。量表數字本身不劃線：那正是使用者停用它的理由。
- **自動解除用該組額度的 reset 時間，而且是勾的當下就算好存起來。** 之後 daemon 推新數字進來，

  三個視窗都沒有 `resets_at` 的那組就只能手動解除。
- **不留例外：執行中與有未讀的也一起收。**（2026-09-08 改）第一版把「執行中／啟動中／卡住／有未讀」
  留在清單上，理由是「使用者正在等的東西不能被藏掉」。實測直接打臉：整批 `cc1` 都有未讀，勾了「已停用」
  側欄一個都沒少，看起來就是壞的。停用是**明講的動作**（「這個帳號的先別給我看」），跟自動門檻不同，
  不該再自作主張留東西下來。代價由下面那行計數交代。
- **只要有 bot 被收走就留一行「N 個 Bot 已隱藏（額度不足）」**：還有可用 bot 的卡片當底部腳註；
  一顆都不剩時當 `.project-empty` 的標題，**底下接同一排 `QuickAddBots` chip**——卡片這時等於沒有
  可用的 bot，就該跟空專案一樣直接給下一步，只是標題說的是「已隱藏」而不是「尚無」，使用者才知道
  bot 沒有不見。既然執行中的也會被收，沒有這行使用者會以為 bot 不見了。
- **被停用的身分那幾顆 chip 標成停用態**（`已停用` 標籤、名字劃掉、`disabled`）：不然使用者會
  再開一顆同樣沒額度的 bot。跟條上、popover 共用 `isQuotaDisabled` 同一份狀態。
- **父列只有在它自己和底下每個子 agent 都可以收時才收走。** 否則子 agent 會連掛的地方都沒有。
- **搜尋中不收。** 同「搜尋中一律展開」：搜到的東西藏起來等於沒搜到。
- 狀態存 `am.disabledQuotaKeys`（localStorage，key = `<host>|<kind>|<identity>`），跟
  `am.collapsedProjects` 同一類：純前端的檢視偏好，daemon 不需要知道。

## bot 列的操作鍵：一顆常駐的 `⋯`（2026-09-08）

- **問題**：四顆 icon（分身／設定／啟動／刪除）疊在名字那行、hover 才浮出來。側欄一窄就蓋住名字，

## Bot 設定改成非模態：不再有蓋住整個 app 的遮罩（2026-09-08）

- **問題**：`.bs-scrim` 是一層 `position: fixed; inset: 0` 的深色遮罩（58% ＋ 2px 模糊），
  只為了接「點外面關閉」這一下。代價是設定一開，整個 app 就被蓋住也點不到：拖圖進對話框
  失效（drop 事件全被遮罩吃掉）、旁邊的 bot 點不到、額度條與 git 列也按不了。
  這張卡本來就貼著齒輪開，形狀是 popover，卻用了 modal 的代價。
- **決策**：遮罩降級成純擺放用的框（`pointer-events: none`、無底色、無模糊），卡片自己
  `pointer-events: auto`。關閉改成 document 上的 `pointerdown`（卡片外按一下，滑鼠與觸控同一條路）
  加上原本的 Escape；髒表單一樣先跳「放棄未儲存的變更？」。同時拿掉 `aria-modal` 與 focus trap
  ——背景可以點，卻把 Tab 關在卡片裡（焦點一離開就被搶回去）會自相矛盾。開場焦點仍落在名稱欄位。
- **界線**：真正的 modal 保留遮罩——`Modal`（新增 Project／新增 Bot／環境設定）的 `.modal-backdrop`、
  `ConfirmDialog`（刪除、放棄變更）的 `.confirm-backdrop`、`BlockedModal` / `MemPaneModal`、
  ≤1024px 側欄抽屜的 `.scrim`、圖片放大的 `.lightbox`。這些都是「先回答我再繼續」，遮罩是對的。
  其餘 popover（`HeadMoreMenu`、`MemPopover`、`ModelPicker`、`Tools`、`IssuesBar`、`AttachButton`）
  本來就用 document 監聽關閉，沒有全螢幕 click-catcher，不用改。
- **代價**：設定開著時鍵盤可以 Tab 到背景去，也不再自動把焦點還給齒輪。換到的是「開著設定
  照樣能用整個 app」——包含把圖片拖進對話框。

## Claude 的更新通知放 header，而不是 toast（2026-09-08）

- **問題**：claude 自動更新後只在 pane 最底下那行印 `✔ Update installed · Restart to update`，
  跟使用者自己的 statusLine 擠同一行、靠右。要一路點進終端才看得到，等於沒通知——本機一整排
  claude pane 可以掛著它好幾天沒人發現。
- **為什麼是 header 的常駐 chip，不是 toast**：它不是一個「發生了」的事件，是一個**一直成立的
  狀態**——在重啟之前都還沒套用。toast 飄過去就沒了，錯過等於沒通知，跟現在一樣；常駐 chip
  才會在使用者下次看這個 bot 時還在。位置跟 `HostBadge` 並排，因為兩者都是「這個 run 的處境」。
- **為什麼點下去就是重啟**：套用更新的動作沒有別的——claude 自己說的就是 restart。所以不另外
  做 API，直接走既有的 `POST /api/bots/{id}/restart`（session 會 `--resume` 接著跑）。
- **為什麼忙碌時要先問一句**：`working` / `blocked` 的重啟會把這一回合切掉，而更新本身一點都
  不急（它已經等在那裡了）。`idle` 直接重啟——那時沒有東西會被打斷，多一個對話框只是擋路。
- **側欄只給一個 8px 的點（`.bot-update-dot`）**，不放按鈕：側欄那一列已經有燈號、身份、模型、
  未讀，窄到放不下第二顆按鈕；點只負責讓人在清單上看見「這台有更新」，真正的動作在 header。
- **掛在 run 不是 bot**：等著被套用的更新是這個 claude process 的事，重啟之後就沒了。

## 執行者那一格叫「併行數」，不叫人數（2026-09-08）

- **為什麼改名**：使用者在意的是「同時會有幾個 task 在跑」，不是側欄多出幾隻 bot。
  舊的「2 人」讓人以為要像排班一樣把工作分給兩個具名的人，於是 PM 也照做——每次只派 n 筆、
  派完就 `wait`，計畫變成一批一批的，而空下來的執行者要等下一批才有事做。改叫「併行數」之後，
  這一格說的就是它真正決定的事：一次最多幾個 task 在跑。API 欄位名仍是 `workers.count`（相容）。
- **為什麼預設 1，不是 2**：多開一個併行位就是多一個 agent 在燒額度，而大多數 issue 沒有
  兩條真正互不重疊的路可以走。多開要是明確的選擇，不是預設就替使用者做掉的決定。
- **為什麼 PM 不指定人**：誰有空是 daemon 才知道的事（它握著 task 狀態），PM 只知道自己派了什麼。
  讓 PM 猜，結果就是猜錯被拒、再猜一次，白白多幾輪 relay。現在 `dispatch` 的 `to` 可以省略，
  PM 想派幾筆就派幾筆，多的排隊；`to` 仍然可以寫，寫了就是**指定那一位**（他忙就排在他後面）。
- **排隊的那一列長什麼樣**：task 列的執行者欄寫「排隊中」（淡一階、無名字），
  而不是原本的破折號——破折號讀起來像「沒有人要做」，排隊中才說得出它會自動被派出去。
  標題列的計數旁加「併行 M/n」，因為「3 個 task」不再等於「3 個在跑」。
- **為什麼分支是開始做的時候才切，不是派工的時候**：排隊的 task 可能等上好幾次合併，
  在收單當下切分支等於從一個過期的整合分支切（SPEC-team §6.2 的保證會破）。
  所以收單只決定分支的**名字**（`<整合分支>-t<seq>`，不再帶執行者短名——名字定下來時還不知道是誰做）。
- 截圖：`docs/screenshots/team-pool/`。

## 手機 RWD：兩個斷點，以及 390px 上讓位的順序（2026-09-08）

- **只有兩個斷點會改變行為**：`≤ 1024px` 側欄變離屏抽屜、圖片暫存從右緣的欄改成底部的條
  （`DRAWER_QUERY`）；`≤ 640px` 是手機（`PHONE_QUERY`）。兩個都寫在 `web/src/hooks/useMediaQuery.ts`，
  CSS 用同樣的兩個數字。styles.css 裡另外那幾個（1240 / 1160 / 1080）只是一階一階收緊邊距與
  標籤，沒有任何行為掛在上面，不算斷點——JS 也不該去讀它們。
  常數本來叫 `MOBILE_QUERY` 卻等於 1024，讀起來像手機，改名成 `DRAWER_QUERY`。
- **手機的 CSS 集中在 styles.css 尾端**：`≤640` 的規則本來散在檔案中段那個區塊裡，新的一律
  往尾端的 mobile 區塊加。分成幾個 `@media (width <= 640px)`（通則、暫存、git 列、標題列、
  終端、sheet），一個主題一段，比一整塊三百行好找。
- **標題列讓位的順序**：模型徽章 → kind 標 → 額度 chip 的身分名 / 視窗名 / 停用方塊 →
  最後才是名字。理由是重複性：讓掉的每一樣在側欄的 bot 列或點開的 popover
  裡都還有一份，名字沒有。齒輪永遠不讓——它是標題列上唯一沒有第二個入口的東西
  （`.main-title` 是 `overflow: hidden`，被切掉的一定是排在最後的，所以齒輪排在徽章前面）。
- **名字沒有下限（2026-09-08 修正）**：原本寫「名字下限 10ch」，但下限與「齒輪永遠不讓」
  互相矛盾——額度 chip 改寫成 `F 剩 26%`（91px）之後標題列只剩 125px，
  `lamp 10 + 7 + 名字 88 + 7 + 齒輪 40 = 152` 排不下，`overflow: hidden` 切掉的就是齒輪
  （390px 上量到只剩 17px 的一條細縫）。改成 `min-width: 0`：空間夠時名字照樣是完整的
  十個字，不夠時它先截尾（本來就有 ellipsis）。名字截短還讀得出是誰（側欄與抽屜各有一份
  完整的），齒輪被切掉就沒有別的路進 bot 設定。
- **百分比始終保留**：額度 chip 寫窗口名 + 剩餘（`F 26%`），風險不能只剩顏色。
- **手機要看得到所有 kind，不是只看目前這顆 bot。** 標題列一顆 chip 會把 claude／codex／grok
  藏起來，點開才看得到等於沒看見。改成標題列底下獨立一列，所有身分與 kind 的 compact chip
  橫向可捲（跟 git 工具列同一種 scroll shadow）；目前這顆 bot 的那格 focused，進來時捲到中間。
  點任何一格仍開底部 sheet 看 5h／7d／Fable。身分名與停用方塊繼續讓位。
- **終端是唯一「字級可以低於 12px」的地方**：`≤640` 其他文字下限 12px，但 `.term` 用 11px、
  內距收到 12px。終端是固定字元格線，多一欄就是多一欄，而它的內容是等寬輸出、不是要讀的散文；
  橫向捲動的成本比字級高得多。
- **圖片暫存在手機預設收合**：展開的托盤在 390px 吃掉約 120px，而它是「等一下也許會用到」
  的東西。留一條 36px 的 bar（圖示＋張數＋展開鍵）。打字時（有文字欄位拿到 focus＝鍵盤彈出）
  把**收起來的**那一條藏掉；展開的不藏——它是使用者自己按開的，而且卡片不能在手指瞄準時
  被一條忽隱忽現的 bar 推走。
- **抽屜是「選完就收」，但開對話框不收**：抽屜蓋在主面板上，選 bot / 專案 / team 之後要讓路，
  連「再點一次已經選著的那顆」也算（那是 390px 上最常見的一種點法）。但從抽屜裡開對話框
  （新增 Bot、刪除專案…）不收——抽屜關著時 `.sidebar` 是 `inert`，一收就把那張對話框
  一起關進去了。
- **對話框在 ≤640 一律全螢幕 sheet**：這不推翻 2026-09-08「Bot 設定改成非模態」那條。
  非模態的用意是「開著設定還能拖圖進對話、還能點旁邊的 bot」——那些手勢在 390px 上本來
  就不存在（沒有拖放、旁邊也沒有東西看得到）。桌機仍然是貼著齒輪開的非模態浮窗。
- 截圖：`docs/screenshots/mobile-rwd/before/`、`docs/screenshots/mobile-rwd/after/`。

## 按鈕色票與 hover / focus 對比（2026-09-08）

- **問題**：`.btn.primary` 沒有自己的 hover 底色，只寫了 `filter: brightness(1.08)`；
  `.btn:hover:not(:disabled)`（0,3,0）的 `--bg-hover` 反而蓋過 `.btn.primary`（0,2,0）的
  `--accent`。結果主鈕一 hover 就是近白底＋白字，量到 **1.18:1**（深色 1.36:1），在
  BotSettingsPanel 的琥珀提醒條上整顆消失。focus 環又寫死 `#76a7ff`，對白底只有 2.4:1，
  跟 hover 的淺灰底糊在一起。掃描全站 17 個畫面狀態、深淺兩套，共 114 筆不合格。
- **決策**：styles.css 開一個 `buttons` 區塊，放 `--btn-*` 色票與四個變體
  （ghost / 實心 / primary / danger）＋ banner 上的覆寫，散落的 hover 規則改成吃 token。
  門檻：文字 ≥ 4.5:1、只有圖示的 ≥ 3:1、hover 與常態的底色差 ≥ 8 L*、
  focus 環對**它坐著的那個面** ≥ 3:1（WCAG 2.2 §2.4.13 的算法，2px `outline-offset`
  讓環落在周圍的面上而不是按鈕自己的底色上）。
- **ghost 的 hover 用「墨色 wash」而不是固定的 `--bg-hover`**：`color-mix(var(--text) 11%,
  transparent)`（深色 15%）。固定色是這次出事的根因——它在白面板上剛好比較深，放到琥珀

## 手機第二輪：終端折行，與標題列第二行拆成兩列（2026-09-08）

第一輪（上面「手機 RWD：兩個斷點」）的斷點與讓位順序不動，這裡補的是它沒處理到的兩件事。
現況與目標見 `docs/goals/mobile-rwd-round2-2026-09-08.md`，截圖在
`docs/screenshots/mobile-rwd/round2-before/` 與 `round2-after/`。

### 終端快照在手機預設折行（可切換）

- **問題**：390px 大概只看得到 45 欄。一個 185 欄的 pane（實測 `C1-fable`）每一行都被右邊
  裁掉，只能一行一行橫捲——等於整個右半邊讀不到。
- **決策**：`.term` 多一個 `.term-wrap`（`white-space: pre-wrap` + `word-break: break-all`），
  預設值跟著 `PHONE_QUERY` 走：手機折、桌機不折。term-bar 上一顆「換行」核取方塊可以兩邊
  互換，選擇記在 `localStorage`（`am.term.wrap`），使用者按過就永遠優先於斷點。狀態放在
  `components/termWrap.ts` 的 module scope，`TerminalTab` / `BlockedPanel` / `HostShellPanel`
  共用，切一次三個面板一起換。
- **代價**：折行會把 TUI 畫的框線與對齊弄亂——所以桌機的預設維持不折。手機上「讀得到」贏過
  「排得漂亮」，而且一顆開關就能換回去。
- `break-all` 是必要的，不是保險：終端的一行常常是一整條沒有空白的路徑或網址，只有
  `pre-wrap` 時它仍然會撐出橫向捲軸。`.term-link` 是 `all: unset`（行內）且本來就帶
  `word-break: break-all`，折行後每一段仍然可點、複製到的仍是接回來的完整 URL。

### 標題列第二行拆成兩列（不是收進 `⋯`）

- **問題**：`.context-bar` 在 390px 排到約 700px。`commit` 那顆剛好被右邊界切成一半，而
  橫捲列在觸控裝置上沒有捲軸可看——使用者只會覺得那顆按鈕壞了。
- **決策**：**拆兩列**，不收進 `⋯` 選單。理由是這一條混了兩種東西：repo 狀態與 git 動作是
  **會按的**（收進選單等於多兩下才 commit 得到），context 與花費是**只看的**（不該為了看一個
  百分比去橫捲）。所以第一列留給 repo + git（照舊橫捲，第一輪那組 scroll shadow 漸層留著），
  第二列給 `.statusline-bar`：`flex: 1 0 100%` 把它擠下去，字級 11 → 12px，排不下就換行而不是
  橫捲，數字 `tabular-nums`。
- **代價**：標題列底下多佔約 20px。換到的是 git 那三顆一次全部露出來（實測 390px 下
  `rt 0 open · +3 −2 ?4 · commit · push · pull` 完整可見，第一列不必再捲）。
- `.statusline-text`（daemon 給的原始 statusline，`white-space: pre`）折不了行，那一種仍舊
  橫捲；`overflow-x: auto` 因此留著，只是有拆成欄位時永遠用不到。
- 帳號欄在手機是 `display: none`，但它還是 `.sl-item + .sl-item` 的前一個兄弟——context 開頭
  因此多出一條沒有左鄰居的分隔線。自己一列之後那條線特別顯眼，所以補了一條把它拿掉。

## 「回合被 API 中斷」要看得見，不是 tooltip（2026-09-09）

背景見 SPEC §4.3a：claude 的連線在回應中途掉了，pane 上只多一行
`⏺ API Error: Connection lost mid-response. …`，hook 與 herdr 照樣把這回合報成 done。畫面上
沒有任何地方看得出來——燈號綠的、回合 `completed`、氣泡裡是半截答案。

### 側欄一個紅記號 + 標題列一顆點得下去的紅 chip

- **決策**：兩個地方都標。側欄那列名字後面一個紅底的「⚠ 中斷」；標題列一顆
  `⚠ 回合被中斷（API 錯誤）` 的紅 chip，點開是原文 + 「重送上一則」。
- **為什麼不只做 tooltip**：斷掉的回合是要**動手**的（重送），不是滑過去才知道的。而且側欄
  在手機上根本沒有 hover——只有 tooltip 等於在手機上沒有這個功能。
- **為什麼不沿用 `.bot-update-dot` 那種小圓點**：那顆是好消息（有新版可以更新），可以安靜。
  這顆是「你以為做完的事其實沒做完」，看漏的代價完全不同，所以給它文字與 `--danger` 底色。
  側欄仍然放不下按鈕，所以記號只負責**被看到**，動作留在標題列。
- **為什麼不是紅燈**：燈號說的是 agent **現在**在做什麼（idle 就是 idle，沒說謊）。把它染紅
  等於把兩件事塞進同一個記號，跟 `unread-turns` 當初分家的理由一樣。

### 「重送上一則」走既有的送出路徑

- **決策**：按鈕就是把對話裡最後一則 user 訊息再送一次 `sendPrompt`（`POST /bots/{id}/prompt`），
  沒有新的 retry API、沒有 `--resume` 之類的特別待遇。
- **理由**：被截斷的是**回應**，不是輸入。既有的送出路徑已經處理好排隊、`delivery` 三態、
  輸入框上鎖與 `client_request_id` 去重；另寫一條只會多一套要維護的邊界。
- **代價**：附件不會跟著重送（只送文字）。原始附件已經是 agent 讀得到的檔案路徑，重送文字時
  那些檔案還在原處；真的要連附件一起，使用者從輸入框重打一次仍然是可行的路。
- 沒有「知道了」按鈕：`runs.turn_error` 在下一個回合開始時由 daemon 清掉，重送本身就是清掉它
  的動作。多一顆「關掉」只會讓人把還沒處理的事關掉。

## 每個畫面都有自己的 URL（2026-09-09）

背景：整個 UI 只有 `/`。重新整理回到首頁、瀏覽器的上一頁沒作用、沒辦法把「這個 bot 的對話」
貼給別人或加到手機主畫面。

### 自己寫 `parse` / `build`，不引 router 套件

- **決策**：`lib/routes.ts` 一對純函式 + `store/routeSync.ts` 的 `pushState` / `popstate`。
- **理由**：路徑只有六種形狀，而且它們都是既有 store 狀態的投影——引一套 router 等於再多一份
  「現在在哪個畫面」的真相，跟 `store.ts` 打架。純函式也才測得起來（`routes.test.ts`）。

### 網址是 store 的投影，不是反過來

- **決策**：側欄與所有「開啟 X」的按鈕維持原本的 `onClick`（走 store），**不改成 `<a href>`**。
- **理由**：一旦有些入口走網址、有些走 store，就要在兩邊都維護「選了 X 要順便關掉 Y」那套
  互斥規則（`selectBot` 會清 project / team / shell / 設定）。改成單向之後，路由只要在最後
  照 `App.tsx` 的 render 順序算一次 `routeOf` 就好。
- **沒做**：goal 允許「bot 列 / project 標題 / team 節點包一層 `<a href>`，讓中鍵開新分頁與
  『複製連結』可用」。這三個都是 `<div role="option">` / `<header>`，裡面還包著收合鍵、`⋯`
  選單、改名輸入框——`<a>` 裡面塞 `<button>` 是無效 HTML，而且會動到拖曳排序與 listbox 的
  鍵盤行為。要做的話應該獨立一個任務，把那三塊的標記一起重畫；現在網址列本身已經可以複製。

### 對話↔終端不留歷史，設定浮窗留

- **決策**：`screenKey` 一樣用 `replaceState`、不一樣用 `pushState`；bot 的 `screenKey` 不含
  分頁，但**含**「設定有沒有開」。
- **理由**：分頁是同一個畫面的兩個面，來回按五次不該讓上一頁要按五次才離開。設定是蓋上去的
  一層，「上一頁 = 關掉它」正是使用者（尤其手機）會有的預期。
- 手機抽屜同理，但它連 URL 都不變：只在 `history.state` 記一個 `{am:'drawer'}` 的記號。

### 壞連結回首頁並說一聲

- **決策**：路徑指向不存在的 bot / project / team / shell 時，`selectBot(null)` 回首頁並
  `notify('info', '…已回到首頁。')`。
- **理由**：連結一定會過期（bot 被刪、pane 活不過 daemon 重啟）。停在一個沒有東西的畫面、
  網址還寫著那個 id，看起來像壞掉；說一句話才知道是「東西不在了」而不是「UI 掛了」。

### `?token=` 不進分享出去的連結

- **決策**：`?token=` 只在第一次載入用，套用路由的第一次 `replaceState` 就把它拿掉。
- **理由**：現在網址是拿來貼給別人的。token 是 daemon 的憑證，不該跟著畫面連結一起流出去；
  transport 在 `GET /api/session` 之後本來就自己快取，網址上留著它沒有任何作用。


## 手機的子 agent 列不寫名字；排序改由 daemon 保管（2026-09-09）

- **子 agent 在 ≤640px 不顯示名字**：一列擠不下，`c1-fable-…` 截完也認不出是誰；子列真正要
  分辨的是身分與模型（它掛在哪個父列底下已經由縮排說明了）。名字留在燈號 tooltip 與整列的
  `aria-label`，讓出來的寬度給模型徽章（原本被截成 `f…`）。桌機不變。
- **排序不再存 localStorage**：`am.botOrder` / `am.projectOrder` 是每個瀏覽器一份，所以同一個
  daemon 在手機與桌機上的順序不一樣（使用者回報）。改成 `POST /api/order` 寫回 config.toml 的
  陣列順序，`projects.position` / `bots.position` 投影進 SQLite，`GET /api/state` 就是權威順序。
  前端只留拖曳當下的樂觀順序，等 `project_changed` 回來就換成 daemon 的。

## 無限併行（2026-09-09）

截圖：`docs/screenshots/team-unlimited/`（`launch-unlimited.png` 建隊面板的「∞ 無限」、
`team-panel-unlimited.png` 三個 issue 同時進行的 TeamPanel）。

### 併行是 issue 級的，不是把一個 issue 硬拆

- **決策**：`workers.count = 0`（UI 上的「∞ 無限」）同時開**多個 issue**，每個 issue 一批
  自己的執行者、一條自己的整合分支；不是「把同一個 issue 拆給更多執行者」。
- **理由**：#48 的實測是 PM 把一個 issue 拆成 `t19‖t20 → t21`，第三段本來就得等前兩段合併——
  同一個 issue 的併行度是**它自己的依賴關係**決定的，加執行者也吃不下去。真正閒著的座位要拿
  佇列裡的**下一個 issue** 來填。而 issue 之間本來就互相獨立（各自的 base、各自的分支、
  各自交付），是唯一可以無腦平行的切法。
- **代價**：PM 要同時管好幾個 issue，所以 `dispatch` / `done` 多了一個必填的 `issue`。這是
  自找的複雜度，但比「daemon 猜這筆 task 屬於哪個整合分支」安全太多——猜錯就是一次合併衝突。

### 每個 issue 先給 1 個執行者

- **決策**：無限模式下每個 issue 只先建 1 個執行者，PM 派工超過在跑的數量才按需再建。
- **理由**：一個 issue 需要幾個執行者只有 PM 拆完 task 才知道。先開 4 個等於為每個 issue
  預付四份額度與四個 pane，而多數 issue 拆出來只有一兩段；先開 1 個、要多少長多少，
  閒置的座位就永遠不存在。

### 6 / 12 是 pane 與額度的天花板，不是預算

- **決策**：同時最多 6 個 issue、每個 issue 最多 4 個執行者、全隊最多 12 個。
- **理由**：這三個數字擋的是**畫面與帳號**，不是花費——花費本來就有 `max_relays` 與
  `max_wall_clock_min` 在管。6 個 issue 已經是十幾個 pane 加一個沒人讀得完的 herdr
  workspace；每個 issue 4 個是既有的 `MAX_WORKERS`（一個 reviewer 序列化審查，再多只會排隊）。
  撞到上限不是錯誤，多出來的 task 就排隊，跟有限模式一模一樣。
- **沒做**：上限沒有做成可調欄位。它們是「這台機器與這個帳號受得了多少」，不是使用者每次
  開隊要重想一次的東西；真的要調應該是設定檔，不是建隊面板上第四個旋鈕。

### 「進行中 2」而不是「第 2 個」

- **決策**：側欄的 issue 計數在多個 issue 同時跑時改寫成 `issue 進行中 2/9`；一次一個時
  維持原本的 `issue 2/9`。
- **理由**：「走到第幾個」預設佇列是一條線。同時開三個時那個數字沒有意義，寫「進行中 3」
  才是實話。耗時也改成取**最早**開跑的那個 issue，否則第一個交付後計時器會突然往回跳。

## 一鍵套用 claude 更新：橫幅放側欄標題底下，忙的跳過而不是排隊（2026-09-09）

背景見 SPEC §6.9。claude 有新版時每顆 bot 各自在 pane 底下印一句 `Update installed · Restart
to update`，套用的方式是重啟。原本每顆都要點一次 header 的 `UpdateBadge`。

### 位置：側欄標題底下、搜尋框上面，整條寬度

- **決策**：`.update-all` 一條橫幅，只在真的有 bot 帶著 `update_notice` 時出現，做完收掉。
- **為什麼不放標題列那排徽章旁邊**：`sidebar-head` 那一行已經擠著 pane / RAM / 連線 / 分頁四顆
  徽章，390px 下本來就要排兩列。再塞一顆會把它擠成三列，而且這顆是「偶爾出現一次」的東西，
  不該長期佔著永遠都在的那一行。
- **為什麼不放對話標題列**：那裡的東西都是「這顆 bot 的事」（`UpdateBadge` 就在那）。批次是
  跨 bot 的動作，放進去會讓人以為只重啟眼前這顆。
- **代價**：手機上側欄是抽屜，要拉開才看得到。可以接受——這是「順手做一下」的維護動作，不是
  需要立刻反應的警訊；真正緊急的（回合被中斷）留在對話標題列。

### 後續（2026-09-09，同日）：觸發那顆搬到額度列，側欄只留結果

- **決策**：`⬆ N` 一顆 chip 掛在額度列（`QuotaStrip`）上，跟每個 kind 的量表排同一列；側欄那條
  橫幅改成只在**按過之後**出現，畫進度與失敗／跳過名單。
- **為什麼推翻上面的「代價可以接受」**：實際用起來，那個代價不只是手機——看 team 面板、群組對話，
  或視窗窄到側欄讓位時，提示一樣不在畫面上，於是「順手做一下」永遠等不到那個順手的時機。
- **為什麼是額度列**：它已經在每個畫面的標題列上，而且本來就是「按 kind 排的全域狀態」——還剩多少
  額度、有沒有新版，是同一個 kind 的兩個數字，讀的人也是同一個判斷（現在能不能動它）。放這裡不用
  新增任何一行永久佔位的東西。
- **貼在 claude 那幾格的右邊**，不是整條列的尾巴：第一版放在列尾（codex／grok／`+N` 之後），
  看起來像「這條列的按鈕」而不是「claude 的狀態」。它講的是 claude 這個 kind，就要跟 claude 的
  量表站在一起；claude 有多個身分時掛在最後一格後面，只出現一次（新版是 CLI 的事，不是某個帳號的）。
- **條上放不下整句話**：chip 只有箭頭與數字，「重啟 N 顆閒置的 Bot」「哪幾顆在忙、為什麼」走 tooltip
  與 `aria-label`，跟同一列的停用開關同一套做法。
- **按下去先問一句**：確認框把「要重啟哪幾顆」「哪幾顆在忙會被跳過」兩張名單攤開來。chip 上只有
  一個數字，tooltip 手機根本滑不到——沒有這一步就是盲按，而送出之後是背景序列跑，沒有取消。
  單顆的 `UpdateBadge` 只在忙的時候問（那是一顆、而且看得到自己在忙）；批次一律問。
- **全部在忙時**：chip 留著但變灰、數字改成在忙幾顆（不是消失）——理由同上一節。
- **不受窄視窗收窄影響**：`tight` 時條上只留焦點那一格量表，claude 那格可能整個不在——這時 chip
  退回列尾，不跟著消失（更新是全域的）。
- **結果仍在側欄**：`重啟中 3/5`、哪幾顆失敗、哪幾顆被跳過與理由——這幾行放不進標題列的 chip，
  而它們才是要動手的部分。chip 上只寫成功幾顆，名單看側欄。

### 忙的跳過，不排隊、不等、不問

- **決策**：`working` / `blocked` / 回合還在飛 / 狀態 `unknown` 的一律跳過，做完把是哪幾顆、
  為什麼列在摘要裡。不排隊等它們閒下來，也不跳確認框問「要不要順便打斷」。
- **理由**：排隊會讓一顆按鈕變成一個要持續盯的背景工作（何時結束？中途新來的回合算不算？）；
  問則是把批次的省事又還給使用者。跳過是唯一不會破壞東西的預設值，而且漏掉的那幾顆等它們
  閒下來以後，橫幅還會在，再按一次就好。
- `unknown` 也跳過：分不出它在不在忙的時候，不動比動安全。
- 按鈕在「有更新但全部在忙」時仍然顯示（改寫成「目前沒有閒置的 Bot」並 disabled）——直接消失
  會讓人以為更新已經套用完了。

### 進度與摘要畫在同一條上

- **決策**：按下去之後那條橫幅就地變成 `重啟中 3/5 · <名字>` 加一條進度條，做完變成
  `重啟完成 · 成功 4 顆 · 跳過 1 顆`，失敗與跳過的名字與理由列在下面，✕ 收起來。
- **理由**：從按下去到看完結果是同一個節奏，中途切到另一個面板反而找不回來。失敗的列在跳過的
  前面：那是要動手的。
- 摘要不會自己消失（只有 toast 會）——失敗的那幾行要留著讓人有時間處理。

## 標題列的收縮優先序：分頁 > 名字 > pane / 記憶體 / 附屬 chip（2026-09-11）

標題列以前只寫了一條「量表一步不讓」（`.main-head > .quota-strip { flex: none }`），沒有規定**不夠時
誰先讓**。結果是溢位時掉出去的永遠是排在最後的東西——使用者量到視窗 1500 / 1520 時「對話／終端」
超出右緣 29px / 9px，分頁根本點不到。分頁是導覽不是資訊，被切掉就沒有別的入口。定成三級：

1. **分頁不讓**：`.main-head > .tabs` 是 `flex: none`，另外加 `position: relative; z-index: 1`
   ——萬一有東西溢位疊上來，被蓋掉的是那個東西而不是分頁。
2. **名字第二**：`.bot-head .main-title` 改成 `flex: 1 0.25 auto`。`flex-grow: 1` 是為了**先吃掉
   標題列中間那段空白**（`flex-basis: auto` 只拿得到 max-content，多的都留在 spacer 手上，量到
   2000px 時空著 127px 而名字已經在截尾）；`flex-shrink: 0.25` 是為了**最後才縮**。搭配
   `.bot-head > .spacer { flex-grow: 0 }`，spacer 只剩「把右邊那組推到底」的用途。
3. **先讓的**：遠端記憶體與附屬 chip（`flex: 0 1000 auto; min-width: 0`，都只是數字，popover 裡
   有完整的）先收到 0。

**量表不在可讓的名單裡**（2026-09-11 使用者：「額度顯示是很重要的訊息，不要去省他的空間；
desktop 都要全顯示」），維持 `flex: none`、五格全開約 770–800px。

### 名字的下限從 168px 降到 3em

原本 `@media (min-width: 721px) { .bot-head .main-title { min-width: 168px } }`（理由是「額度條再長
也不能把名字壓成 `0-op…`」）。這條跟上面兩件事湊不齊：側欄開著時視窗 1500–1560px 的標題列只有
1004–1064px，光是選單鍵 36 + 量表 ~770 + 分頁 110 + 內距 32 + 間距 40 就吃掉整條，168px 的下限
會把分頁推出右緣 56–116px。使用者的優先序是分頁 > 名字，所以下限降到 3em（名字一定還看得見一

## 「正在看的那一顆」不列進標題列下面那一排（2026-09-11）

`.unread-bar` 的釘選那組（★）本來把所有釘起來的 bot 都列出來，包含**當前正在看的那一顆**。
那顆晶片是多餘的：標題列上就寫著同一個名字，它已經是畫面本身，點下去什麼也不會發生。
排掉之後空出來的寬度留給真的要跳過去的那幾顆；三組都空時整列照舊消失、不佔高度。

「剛跑完」「進行中」兩組的排除規則沒有動（`isPinned` 仍然用完整的釘選清單），只有畫出來的
那一組少掉當前這顆。`.unread-chip.pinned.current` 這個樣式因此沒有對象，一併拿掉。
截圖 `docs/screenshots/header-name-width/`。

### 更正（2026-09-11 稍晚）：不是拿掉，是**固定住並標成 focus**

使用者看過之後推翻上面那條：「調整 剛跑完bot與星號列表，要固定，即使現在正在 view 也是
focus 而不是消失。」這一列不只是「還沒看的通知」，它同時是跨 bot 的定位條——正在看的那顆
從列上消失，等於把你現在的位置從地圖上擦掉，後面幾顆還會往左跳。

改成：

- **★ 釘選那組**：不再排除當前 bot，釘了就一直在，正在看的那顆套 `current`。
- **「剛跑完」那組**：點進去那一刻 `selectBot` 會同步 `markBotRead` 把未讀清成 0，晶片本來會
  在手指底下消失。現在只要它還被選著就留在原位（未讀數字拿掉——你就在看它了，不要畫一顆
  `0`），切到別顆之後才依原本的規則離開。
- **位置本來就固定**：三組都是從 `bots` 陣列濾出來的，順序不是未讀時間也不是跑完時間，所以
  一顆晶片只要還在列上，位置就不會變。要記的只有「它在被選走的前一刻有沒有未讀」。
- 那份記憶放在 **模組層**（`UnreadChip.tsx` 的 `keepSelectedRow`），不是 `useState` / `useRef`：
  `App.tsx` 是 `<ChatPanel key={botId}>`，換 bot 會把整棵（含這一列）重新掛載，元件自己的
  記憶正好在需要它的那一刻被清空。畫面上同時只有一列，一份模組層的記憶就夠。
- 刻意**不**讓「從來沒有未讀過的 bot」黏上來：不然隨便點一顆都會多一顆晶片，三組全空時整列
  就不會消失了（那一條沒變）。
- focus 的樣子：實線 accent 邊框 + accent 底 + 一圈 `box-shadow` ring + 粗體。原本 `current` 是
  虛線邊框（意思是「不用再點一次」），但那個畫法看起來像被停用；而且「剛跑完」那組本來就是
  accent 底，光換邊框顏色分不出來。ring 用 `box-shadow` 所以不佔版面，不會讓整列位移。

實測（1600px，造了兩顆有未讀的 bot）：點第一顆 → 它留在 x=343 並變 focus、未讀數字消失，
其餘晶片順序不變；再點第二顆 → 第一顆才離開；切到釘選那顆 → 釘選那顆變 focus 且照樣在列上。
截圖 `docs/screenshots/header-name-width/unread-focus-*.png`。

**已知的小位移**：被選中的那顆自己不動，但排在它**後面**的晶片會往左移約 19px——因為未讀數字
那顆小徽章被拿掉了。要完全不動就得替那個徽章留一個固定寬度的空位，那會在晶片裡留一塊看不出
用途的留白，暫時沒做。

### 再補（2026-09-11）：釘選晶片有未讀時也要亮起來，而且跟 focus 分得開

釘選那排本來只在名字後面多一個小數字，一排 ★ 看過去分不出哪一顆「有東西等你看」。順手把這一列
的兩個狀態拆成**正交**的兩套畫法，三組共用：

| 狀態 | 意思 | 畫法 |
| --- | --- | --- |
| `unread` | 有東西等你看 | accent 底色 + accent 文字（+ 原本就有的未讀數字徽章） |
| `current` | 你正在看這一顆 | accent 邊框 + 一圈 `box-shadow` ring + 粗體，**不碰底色** |

兩者可能同時成立（視窗在背景時，正在看的那顆又跑完一輪），疊起來仍分得出是哪一種。
為此 `.unread-chip` 的基底底色從 accent 改成中性，底色改由 `.unread-chip.unread` 決定——
「剛跑完」那組因此也要自己套 `unread`（黏住的那一顆未讀已歸零，就只剩 focus 的 ring，不再是
亮的，語意剛好對）。`.unread-chip.pinned`、`.pinned.current`、`.working.current` 那幾條只是為了
互相蓋底色而存在，拆開之後沒有對象，一併刪掉。

★、名字、進行中的圓點都照舊：這是**加一層狀態**，不是把釘選換成「剛跑完」那一組；去重規則
沒變，釘起來的一律只出現在釘選那組。

實測（1440 / 390，造兩顆有未讀的釘選 bot）：`.pinned.unread` 的底色是 `rgb(38,55,92)`，
沒未讀的釘選晶片是 `rgba(0,0,0,0)`，正在看的那顆底色同樣透明但多一圈 ring。
截圖 `unread-focus-05-pinned-unread-1440.png`、`unread-focus-06-pinned-unread-390.png`。

## 標題列的更新 chip：文字縮成 `${kind} 有更新`，批次蓋得到就不畫（2026-09-11）

**文字**：原本寫「有更新 · 重啟套用」。改成只寫 `${bot.kind} 有更新`（`claude 有更新`／`codex 有更新`），
118px → 104px。「點一下會做什麼」移到 `title` 與新加的 `aria-label`，不印在條上——第一排的寬度
要留給名字（見上面的收縮優先序）。

**條件隱藏**：額度列最左邊那顆綠色 `⌃⌃ N`（`UpdateQuotaChip`）按下去會一次重啟
`updateBatchCounts(bots, runs, hasInFlightTurn).ready` 裡的每一顆。當前 bot 落在那份名單裡時，
右邊那顆本來就會把它一起重啟，標題列再放一顆等於同一件事講兩次，還吃掉 118px。所以
**`variant === 'chip'` 在 `ready` 名單裡就不畫**。

批次**蓋不到**的三種留著，因為只有這顆能單獨重啟它們（規則全部沿用 `lib/updateBatch.ts`，
那份跟 daemon 的 `bulk_restart.rs::plan` 一字不差，這裡不另外寫一套）：

- 在 `busy` 名單（`working` / `blocked` / 狀態不明 / 還有回合沒收掉 / 還在啟動關閉中）——批次會跳過它。
- `managed_by !== 'user'`（子 agent、team 成員）——`updateBatchCounts` 根本不算它們。
- 不是 claude——批次只處理 claude。

另外「已經按開確認框」或「正在重啟中」時也照畫，不然狀態一轉成 `ready` 會把使用者面前的
對話框整個抽走。側欄那顆 `variant="dot"` 完全不受影響（它在 bot 列上，跟標題列的寬度無關）。

selector 回**純布林**（`.ready.some(...)`）而不是陣列：`updateBatchCounts` 每次都回新陣列，
回陣列連 `useShallow` 都擋不住，React 會噴 `getSnapshot should be cached`（`UpdateQuotaChip.tsx`
的註解裡寫過同一個坑）。

截圖 `docs/screenshots/header-name-width/`：`batch-hidden-*`（閒置、在 `ready` 裡 → 第一排只剩
燈號／名字／齒輪／★，名字完整）、`badge-kept-*`（執行中、在 `busy` 裡 → chip 照留，寫
`⌃⌃ claude 有更新`）。

## 無障礙語意：側欄是 list 不是 listbox，快速選單是 menu（2026-09-11，#11）

外觀一律不動，只換角色與鍵盤行為。截圖在 `docs/screenshots/a11y-issue-11/`。

- **側欄 bot 列是 `listitem`，不是 `option`。** option 裡不准有互動子元素，而 bot 列裡有收合鈕、
  改名、`⋯` 選單——螢幕閱讀器會把它們吃掉。外層 `.sidebar-scroll` 改成 `<nav aria-label="Bot 清單">`，
  每個專案的 bot 包一層 `.bot-list`（`role="list"`）；子 agent 清單在 DOM 上仍是父列的兄弟（排版要這樣），
  用父列的 `aria-owns` 掛回它底下。「選取中」改用 `aria-current`，專案標題鍵的 `aria-pressed` 也換成
  `aria-current`（它不是開關，再按一次不會放開）。列本身照舊 `tabIndex=0`、↑/↓ 換 bot、Alt+↑/↓ 排序。
  前面「網址是 store 的投影」那節說的「listbox 的鍵盤行為」就是這一套，行為沒變，只是角色換了。
- **專案標題列 `<header onClick>` 留著、不給 tabIndex。** 它只是把滑鼠命中區延伸到鍵之間的空隙；
  鍵盤等價是裡面的 `ProjectTitle` 按鈕（同一個 `selectProject`）。再給 header 一個 Tab 停點等於同一件事按兩次。
- **分頁加 ←/→/Home/End，但不做 roving tabindex。** 本檔「只用 Tab、Enter、Space、Escape 可完成切換
  聊天/終端」是驗收條件，roving 會讓沒被選的分頁 Tab 不到。方向鍵是多給的路（`components/tabKeys.ts`）。
  對話／終端下面那塊包一層 `.tab-panel`（`display: contents`，只為了掛 `role="tabpanel"` 與 id）。
- **模型快速選單是 `menu` + `menuitemradio`（Fast 是 `menuitemcheckbox`），不是 radiogroup。**
  點一下就 PATCH 並關掉，那是選單的行為；radio 的「方向鍵即選取」會每按一下送一次 PATCH。
  打開時焦點落在已勾選的那一項，方向鍵只移焦點，Enter/Space 才套用，Esc／Tab 關掉並把焦點還給觸發鍵
  （`hooks/useMenuKeys.ts`，「用現有 agent 安裝」的 Bot 選單也用這一支）。
- **目錄選擇器的 `›` 不再是按鈕。** option 裡不能有按鈕，整列就是 option；`›` 是滑鼠捷徑，鍵盤走 Enter／→。
  焦點一直留在篩選框（`role="combobox"` + `aria-activedescendant`），點列時也不搶焦點。

## blocked 的編號選單：在 web 上直接點，不要去按 ↓↓↓ Enter（2026-09-12）

使用者實拍（手機 390px）：`carbis` 停在 claude 的 AskUserQuestion 選單上，畫面是終端快照＋
`Enter / Esc / y / n / ↑ / ↓ / ctrl+c` 七顆鍵。要選第 4 項得按三次 ↓ 再 Enter，而選項寫什麼
得去戳 11px 的等寬字，長的說明還被終端寬度截掉（`#21 的評價 dem…`）。

決策：**前端**從終端快照解析編號選單（`web/src/lib/tuiChoices.ts`），畫成一列一個 44px 的
按鈕（`BlockedChoices.tsx`）。daemon 不動——`daemon/src/tui_prompts.rs` 那套是「daemon 要不要
替使用者按掉」才需要的判斷，這裡只是換一個畫法，狀態仍然只有終端一份。

取捨：

- **送 ↓／↑ × n ＋ Enter，不送數字鍵。** 選單腳註自己寫的就是這兩顆
  （`Enter to select · ↑/↓ to navigate`），每一種編號選單都吃、超過 9 項也算得出來；數字鍵
  是否直接選取各家 TUI 不一致（claude 的滿意度問卷還要再補一個 Enter，見 `tui_prompts.rs`），
  猜錯就等於替使用者打了一個字進去。方向是從游標往目標算的，中途不會走到頭尾，所以「到頂
  會不會繞回最後一項」這種各家不同的行為碰不到。
- **送出前先重讀一次畫面。** ↓ 的次數是相對值，而手上的快照最多是一秒前的。點下去先
  `GET /terminal` 重讀、重新解析、比對選項沒變，才用**當下**的游標位置算按鍵；變了就一顆
  都不送，提示「畫面在這中間換過了」。
- **認不出來就整塊不長。** 四個條件全中才算數：至少兩項、編號從 1 連號、**剛好一個**游標
  記號（`❯`／`>`）、整塊在畫面底下。少一個就回 `null`，畫面照舊是終端快照＋按鍵面板
  （`mobile-390-fallback.png`）。按鍵直接進別人的終端，寧可少一個捷徑也不要認錯。
- **說明不再截第二次。** 終端折成好幾行的說明接回一段（中日韓字元之間不補空白）後原樣顯示，
  **不加行數上限**——使用者的抱怨就是「被截掉」。TUI 自己用 `…` 截掉的字救不回來，那要靠把
  pane 移到自己的分頁（`BlockedModal` 的窄 pane 警告已經在講這件事）。
- **游標位置不只靠顏色**：左邊 3px 藍邊＋編號反白＋「游標在此」四個字，手機也留著。
- **面板（`BlockedPanel`）認出選單後把終端快照收起來**，標題列多一顆「看終端」。那條面板在
  手機上只有 300px 高，而快照裡要看的東西已經全部攤成可以點的清單了。全畫面
  （`BlockedModal`）**不收**：那個視窗本來就是「要看完整畫面才決定得了」才開的；只有 ≤640px
  把終端縮成 110px 一條、清單拿走剩下的高度——390px 寬讀 185 欄的畫面本來就只看得到左上角。
- codex 的升級提示（`> 1. Update now / 2. Skip / 3.`）**讓給** `CodexUpdateHint`，那裡多一顆
  「先看改了什麼」。同一件事不長兩排按鈕。

## blocked 選單模式：多分頁 ＋ 多選的 AskUserQuestion（2026-09-12 第三輪）

使用者實測 `carbis`：「第二個分頁的問題沒有辦法正確解析」——整塊選單長不出來，退回終端快照

## blocked 選單模式：說明預設收起來，一列一行（2026-09-12 第四輪）

使用者：「調整不需要預設展開／而不展開的情況下也要可以過滑動上下」。實拍那張六個選項、每項
三到五行說明，攤開要滑三四屏才看得完**一組**選項——等於還是在終端裡找東西，只是字變大了。

量到的結果（真機 carbis 六選項，390px）：列高 44–47px、整份清單 950 → **300px**，問題、六個
選項、送出、Esc 一屏看完，不用捲。

- **▸ 是整列按鈕的兄弟，不是子元素**：`<button>` 裡不能再包 `<button>`，而整列本身就是「選
  這一項」。點 ▸ 只展開說明，一顆鍵都不會送出去；整列點下去仍然是選取／切換勾選。
- **▸ 只長在真的有東西可看的列上**：有說明的（React 給的 class），或標題被截尾的——後者量

  render，而 React 不管 `data-*`，重畫也不會洗掉）。展開中的那列不量，它的標題本來就折行了。
- **展開／收合不跳畫面**：按下去之前先記住那一列離捲動容器上緣多遠，重畫完把 `scrollTop`
  補回差值。量到的是展開前後都停在 top 94px、`scrollTop` 149 沒動。被點的那一列一定在畫面上
  （不然按不到那顆 ▸），所以錨點永遠是使用者正在看的東西。
- **游標換到哪一項就把那一項捲進視野**（`scrollIntoView({ block: 'nearest' })`，只在游標真的
  變了時動）：↑／↓ 是直接送進終端的，畫面不跟上就等於在盲按。`nearest` 代表本來就看得到時
  不會亂捲。
- **捲動容器沒有動**：全畫面仍然只有 `.blocked-modal-body` 一條主捲軸（收合後 448/258 仍捲得
  動），面板仍然跟著聊天區捲。收合不是把外層改成不可捲。

退路沒有動：解析不出來整塊不長，畫面照舊是終端快照＋七顆鍵＋那條 sub（量到 term 1 塊、
keypad 7 顆、沒有 Esc 條）。第三輪的多分頁＋複選照舊，測試 17 項全過。

## blocked 選單：小面板自己要能捲，review 頁的分頁列要畫得出來（2026-09-12 第五＋七輪）

**無法滑動（第五輪 A）**：使用者在 390px 上滑不動、送出鈕永遠在畫面外。量到的祖先鏈是
`.blocked-choices 432/432 → .blocked 551/550 → .chat 582/**667** → .main 844/929 →
.app overflow-y: hidden`——對話分頁平常是「訊息列自己那一層」在捲，而 blocked 面板在它外面，
所以選單一長出來就沒有任何一層收得住，`.app` 直接裁掉。

決策：**認出選單時讓這塊面板自己成為捲動容器**（`max-height: 70svh; overflow-y: auto`），
不動 `.chat` / `.app` 的溢出設定——那是整個版面的地基，動它會牽到訊息列、輸入框與終端分頁。
沒有選單時也不動（那時面板高度本來就被終端快照的 `max-height: 300px` 收著），全畫面視窗那條
主捲軸也沒有第二條。面板自己會捲之後，分頁列與問題同樣釘在它的上緣。
量到（390×560 逼出溢出）：`.blocked` 324 高／562 內容、`overflow-y: auto`，捲 238px 之後
最後一顆按鈕進到視窗內；改之前整條鏈沒有任何一層可捲。

**review 頁點不到分頁（第七輪）**：使用者走到最後那頁，看到答案不對卻回不去改。根因是分頁列
原本只在「問題正上方那一行」找，而 review 頁的分頁列與選項之間隔著一整段 Review：

```text
←  ☒ 編輯方式  ☒ 功能  ✔ Submit  →
Review your answers
 ● 文章是誰寫、怎麼上稿？
   → 非工程師要能自己發
Ready to submit your answers?
❯ 1. Submit answers
  2. Cancel
```

改成從選單起點**往上找一段**（20 行內，遇到分隔線或正文符號就停）取最靠近的那一條；一般
選項頁那條本來就在問題正上方，兩種版型都吃得到。順便把中間那段 Review 解析成「每題 →
目前答案」，畫成可以點的列——使用者在這一頁最想確認的就是自己答了什麼，而那段原本只存在
收起來的終端原文裡。點一題就走回那個分頁改。

- **切分頁改送 ←／→**，沒反應才退回 `tab`／`shift+tab`：分頁列兩端畫的就是那兩顆箭頭，而且
  它們在別處沒有副作用；`shift+tab` 在 claude 主輸入列是「切換權限模式」，萬一沒被對話框收走
  就會改到使用者的 session。換頁一律不送 space／數字／Enter——換頁不該改到任何答案。
- **「現在在第幾個分頁」改由解析器猜**（第一個還沒答的；全答完就是 `✔ Submit` 那格），UI 照舊
  用虛線框標示並在 tooltip 寫明是推測。review 頁量到 `tabAt = 2`（Submit），跟實機一致。
