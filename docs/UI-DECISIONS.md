# UI 優化決策清單（Codex gpt-5.6-sol，依 2026-09-06 實機截圖 200–204）

> 決策者：Codex sol；實作者：Grok；輸入截圖：`docs/screenshots/200-v40-chat-dark.png` … `204-v40-settings-dark.png`。

### [優先級 P0] 群組聊天必須明確指定收件者與發言者

- 現況問題：202 中使用者訊息只有氣泡下方的小字 `→ @am-claude` 表示收件者；agent 名稱也放在回覆氣泡下方。快速掃讀時難以立即判斷「誰對誰說話」。輸入框只靠 `@bot 或 @all…` placeholder，容易漏填或誤送給全部 bot。
- 決策：在群組 `.composer` 上方加入 36px 高的收件者列，包含 `@all` 與各 bot chip，間距 8px；未選收件者時停用送出。選擇器只負責產生既有 `@bot` 語法，不改協定。`@all` 使用警示色並顯示「3 個 bot」。每則訊息在氣泡上方放 18px 高 metadata：左側為 `am-claude · Claude` 或 `你 → am-claude`（13px/600），右側為時間（11px）。Claude、Codex、Grok 分別使用琥珀、藍、石墨色的 3px 標記，但名稱文字必須同時存在，不能只靠顏色辨認。
- 驗收方式：隨機查看連續 10 則群組訊息，1 秒內可說出發言者與收件者；未選對象無法送出；選 `@all` 時畫面明確顯示實際收件 bot 數量。

### [優先級 P0] 降低停止、刪除錯誤操作風險

- 現況問題：200–205 的每個運行中 bot row 都固定顯示紅框「停止」，頂欄又重複一個；大量紅色搶過名稱、模型及狀態，且容易停止錯誤 bot。204 的刪除操作同樣缺少足夠的對象確認。
- 決策：側欄 bot row 不再常駐紅色停止按鈕，改為尾端 32×32px 操作選單，僅在選取、hover 或鍵盤 focus 時出現；「停止」移入選單。當前 bot 頂欄保留一個 64×32px「停止」，點擊後以 360px 寬確認框顯示 bot 與 project 全名。「中斷」維持一鍵操作但使用中性色。刪除 Bot 必須輸入 bot 名稱後才能確認。紅色只出現在確認階段、危險區及 hover，不作為常態列表色。
- 驗收方式：一般聊天畫面最多只有一個常駐危險操作；任何停止或刪除確認都能看到完整 bot/project 名稱；按 Escape 或「取消」不會改變程序狀態。

### [優先級 P1] 收斂主要版面寬度與閱讀動線

- 現況問題：在 2048px 截圖中側欄約 421px，訊息左右端相距超過 1400px；長回覆行寬過長，短對話又形成大量無意義留白。
- 決策：側欄寬度設為 `288–344px`，桌面預設約畫面寬度的 18%；聊天區建立置中的 1180px 最大寬度 conversation lane。agent 氣泡最大 840px，使用者氣泡最大 640px，且皆不得超過 lane 的 78%。頂欄高 56px、composer 高 76px；訊息區水平 padding 24px、同一發言者訊息間距 12px、不同回合間距 24px。視窗低於 1024px 時側欄改為可開關的 overlay。
- 驗收方式：在 1280、1440、2048px 寬度下皆無水平捲動；一般中文段落每行約 35–50 字；左右對話不需大幅轉動視線即可追蹤。

### [優先級 P1] 精簡側欄資訊層級

- 現況問題：專案路徑即使在 421px 側欄仍被截斷；每個 bot 同時呈現 lamp、kind、model、identity、齒輪與停止按鈕。底部的新增、主機、身分與 kind 顯示設定又與主要清單競爭注意力。
- 決策：project header 高 48px，第一行顯示專案名稱，第二行以 11px 顯示截斷路徑；完整路徑由 tooltip 提供。bot row 高 52px：第一行為 8px lamp、14px/600 名稱與狀態；第二行最多顯示兩個 20px 高 metadata badge，其餘放入詳情。project 操作 icon 只在 selected/hover/focus 顯示，點擊區至少 32×32px。底部只保留兩個 36px 高的「新增 Project／新增 Bot」，主機、身分、kind 顯示合併至「環境設定」disclosure。
- 驗收方式：側欄同時顯示 8 個 bot 時仍能快速掃讀名稱與運行狀態；沒有一列因控制項擠壓而看不到 bot 名稱；完整路徑始終可查。

### [優先級 P1] 將缺少 CLI 提示改為情境式警示

- 現況問題：200–205 中「有主機缺少 agent CLI」區塊約佔 140px 高，即使目前正在使用 Claude、缺少的是 Grok，仍持續壓縮所有聊天及設定畫面；灰色 summary 又不像警示，藍色安裝按鈕反而最搶眼。
- 決策：只有當目前 bot 或群組收件者受到影響時，才在頂欄下方顯示 44px 高警示列；內容為 13px 文字、32px 高次要按鈕與展開箭頭。無關當前工作時，縮成頂欄的琥珀色狀態圖示及數量。摘要採「m4p 缺少 Grok CLI」，多筆時顯示「1 台主機缺少 2 個 CLI」；詳細清單展開後最大高度 160px。
- 驗收方式：進入未受影響的 Claude 對話時不再出現大型警示；受影響 bot 的訊息區頂端仍不低於畫面 y=120px；從摘要可直接知道主機及缺少的 kind。

### [優先級 P1] 把額度資訊拆成可辨識的 kind 單元

- 現況問題：頂欄目前把多組 `5h 剩…／7d 剩…` 串在同一行，主要依靠小圖示區分 kind；202 又同時存在群組成員 chip，資訊容易黏在一起。`1%` 與 `98%` 的風險層級也不夠明顯。
- 決策：每個 kind 使用獨立 132×40px quota pill，左側顯示 16px icon 與 12px kind 名稱，右側上下排列 `5h 1%`、`7d 77%`（11px）。剩餘量低於 10% 使用紅色、10–29% 使用琥珀色、30%以上使用一般文字加綠色進度標記；百分比始終保留，不能只用色彩。畫面寬度低於 1600px 時只顯示目前 kind 或最低額度 kind，其餘收入「全部額度」popover；無資料明確顯示「無資料」，不只放破折號。
- 驗收方式：使用者在 2 秒內能指出「哪個 kind、哪個週期即將耗盡」；1280px 寬度下不與群組成員或停止按鈕重疊。

### [優先級 P1] 重建淺色主題的對比角色

- 現況問題：201 中 canvas、composer、停用控制項及訊息 metadata 都落在相近的淡灰色；時間、`hook` badge、路徑及未選狀態偏弱，選取中的側欄 row 也不夠明確。
- 決策：淺色使用 canvas `#EEF1F5`、surface `#FFFFFF`、subtle surface `#F6F8FA`、主文字 `#1B2430`、次文字 `#5E6A78`、邊框 `#C8D0DB`、primary `#2F6FE4`；選取列用 `#E6EEFF` 加左側 3px primary。深色使用 canvas `#15191F`、surface `#1D222A`、raised surface `#262C35`、主文字 `#F1F4F8`、次文字 `#A8B2C0`、邊框 `#3C4653`。composer 必須是 surface，而非與 canvas 同色；重要文字不得靠低 opacity 製造弱化。
- 驗收方式：兩個主題的普通文字對比至少 4.5:1，控制項邊界與 focus ring 至少 3:1；100% 縮放下可直接讀出時間、來源 badge、路徑與停用原因。

### [優先級 P1] 統一訊息結構與輸出層級

- 現況問題：200/201 中時間與 `hook` 標記游離在氣泡下方；短回覆如 `1`、`V40-OK` 的容器比例不一致；一般 agent 回覆、hook 輸出及程式碼主要依背景深淺區分。
- 決策：所有訊息固定為「18px metadata row＋4px 間距＋bubble」。bubble 不設最小寬度，最小高度 36px，padding 為上下 10px、左右 14px，圓角 14px；正文 15px/24px，程式碼 13px/20px。agent 使用中性 surface＋1px border，使用者使用 primary；hook／系統輸出增加 3px 中性左側 rail 與 monospace source badge，不使用一般 agent 樣式。訊息列表頂部與底部保留 16px scroll padding，避免首尾內容被裁切。
- 驗收方式：短回覆會貼合內容，不再形成不必要的大盒子；不閱讀文字也能分出使用者、agent 與系統輸出；長程式碼只在 code block 內水平捲動。

### [優先級 P1] 重排新增 Bot 表單並消除模糊預設值

- 現況問題：203 以 `foo-claude` 作為名稱提示，kind 預選 Claude、模型與身分都只寫「預設」，使用者無法知道實際會採用什麼；表單直接插入清單並把其他 bot 推到下方。
- 決策：新增流程在側欄內切換成暫時性 sheet，而不是插入清單；頂部顯示「新增 Bot · agents-manager」與返回按鈕。欄位順序固定為「kind → 模型 → 身分 → 名稱 → 人設」。kind 預設為該 project 最近使用且已安裝的 CLI；沒有紀錄時選第一個可用 CLI，未安裝者停用並標註原因。模型改寫為「使用 CLI 預設」，身分改寫為「不指定身分（本機預設）」。名稱預填唯一的 `{kind}-{序號}`，人設預設不設定並維持收合。欄位高 40px、垂直間距 16px；名稱無效或 CLI 不可用時停用「新增並啟動」。
- 驗收方式：畫面上不再出現無法解釋的「（預設）」；只用鍵盤即可依正確順序完成建立；任何可按下的建立操作都有有效名稱及可用 CLI。

### [優先級 P1] 將 Bot 設定改為固定寬度側面板

- 現況問題：204 的設定表單只占主內容左半部，右側留下大面積空白；不可修改的 kind 被做成 disabled input，容易被誤認為表單錯誤；關閉鈕與儲存鈕相距過遠。
- 決策：設定改為右側 520px drawer，可在 `440–560px` 間響應；低於 1180px 時才占滿主內容區。header 高 56px、body padding 24px、欄位間距 20px、sticky footer 高 72px。kind 移到標題旁作 read-only badge，不再做 disabled input；編輯順序為「名稱 → 模型 → 身分 → 人設」。未修改時停用儲存；有未儲存內容時關閉須確認。危險區與一般設定間隔 32px，刪除確認在區塊內展開。
- 驗收方式：204 尺寸下不再出現超過 560px 的無效表單寬度；關閉後回到原聊天捲動位置；修改尚未儲存時不會因誤按關閉而遺失。

### [優先級 P2] 為無 bot、無訊息與停止狀態提供不同空狀態

- 現況問題：現有畫面在訊息少時只剩大片空白；未運行的 Grok 只以空心 lamp 和「啟動」表示，缺少「現在能做什麼」的主內容引導。
- 決策：空狀態最大寬度 360px，置中於 conversation lane；icon 40px、標題 16px/600、說明 13px/20px、元素間距 12px。無 bot 顯示「此專案尚無 Bot」及 40px 高新增按鈕；無訊息顯示「開始交代第一個任務」並自動 focus composer；bot 已停止時保留歷史，在 composer 上方顯示 48px 狀態列與「啟動」按鈕，composer 停用並說明原因；daemon 斷線則顯示全域連線狀態，不偽裝成 bot 空狀態。
- 驗收方式：首次進入每一種狀態時，測試者在 5 秒內能指出下一個可執行動作；停止狀態仍可閱讀歷史，但無法誤以為訊息已送出。

### [優先級 P2] 統一 icon、tab 與鍵盤操作規格

- 現況問題：project header 的終端、加號、關閉與 bot 齒輪都很小且缺少文字；203 中藍色加號只靠狀態色表達用途，鍵盤 focus 也不明顯。
- 決策：頂欄及 project 操作點擊區統一為 36×36px，bot row 內最小 32×32px；`.tab` 高 36px、左右 padding 14px。所有無文字 icon 在 hover 400ms 後顯示動作名稱及作用對象。鍵盤 focus 使用 2px `#76A7FF`、offset 2px；hover、selected、focus 必須是三種可區分狀態。
- 驗收方式：只使用 Tab、Enter、Space、Escape 可完成切換聊天/終端、開啟設定、新增 Bot 與取消操作；每個 icon 都有可見 tooltip，focus 不會被背景或裁切隱藏。

### 不要改什麼

保留「左側依 project 分組、右側聊天」的核心模型；保留使用者靠右、agent 靠左的對話方向；保留 lamp 對運行狀態的即時提示、kind/identity badge 的緊湊語彙、聊天/終端 tab，以及設定頁已獨立出的危險區。不要改成卡片牆、三欄 dashboard 或為每個 kind 填滿整個訊息背景；kind 色彩應繼續只作辨識標記。所有調整都應保留既有指定 class 契約。

## 2026-09-07 圖片暫存托盤（新增取捨）

- **右緣一條可收合窄欄，而不是右下角浮動托盤。** 浮動托盤會蓋住訊息與輸入框，而這個區域
  是「常駐」的（不屬於任何對話），一直懸在內容上方比缺點更明顯。窄欄是 `.app` grid 的
  第三格，收合 38px、展開 208px，關掉的偏好會記住。`≤1024px` 移到**底部**同樣是 grid 一格，
  不做 sheet：手機上 sheet 蓋掉的正好是輸入框。
- **點一下就放進目前對話，拖放只是桌機的加分項。** 觸控裝置沒有 HTML5 拖放，若只做拖放，
  手機就完全用不到這個功能。所以「點」是主要動線，兩個平台一致。
- **複製，不是搬移。** 圖片放進對話後仍留在暫存區——同一張截圖常常要餵好幾隻 bot，而誤觸
  也不該弄丟唯一的一份。移除是明確的動作（× 或清空），並在卡片上閃一下「已放入」當回饋。
- **暫存區不上傳。** 附件 id 綁收件 bot 的 project，先上傳等於先賭一個對象；圖片放在暫存區
  期間只有瀏覽器記憶體裡的 `File`，直到它真的被丟進某個對話。代價是重新整理就沒了，
  這是需求接受的取捨。
- **放大預覽固定在托盤外緣，不跟著游標。** 跟著游標的預覽會抖，而且一定會經過卡片與它的
  移除鍵；固定在窄欄左側（底部托盤時在整條之上）位置可預測，也是唯一能保證「不擋移除鍵」
  的做法——只避開卡片還是會壓到標題列的 ＋ / ✕ / »。預覽一律 `pointer-events: none`。
- **觸控用長按開預覽，不用「點一下」。** 點一下已經是「放進對話」，那是手機上唯一的主要
  動線，不能拿去換預覽；長按開、再點一下收。桌機 hover 有 180ms 延遲，focus 立即（鍵盤
  使用者要的是資訊，不是防手滑）。
- 上面「不要改什麼」那條（保留左側 project 分組、右側聊天的核心模型）不受影響：暫存區是
  版面外緣的一條 utility 欄，不是第三個內容欄，空的時候只有標題列與一行說明。

## 2026-09-07 「這回合的提問」浮窗（新增取捨）

- **浮窗，不是版面裡的一列。** 它只在回合進行中存在；若讓它佔掉高度，每個回合的開始與
  結束都會把整串訊息上下推一次。浮在 `.msg-list` 上緣（`.lastq-slot`，`position:absolute`）
  只蓋住捲軸最上緣那一段——那裡通常是已經讀過的舊訊息，而視線在等待時是盯著底部的。
  代價是它確實蓋住東西：所以底色不透明（半透明會讓兩層字疊在一起）、有關閉鍵，
  而且只在「有進行中的回合」時出現。
- **釘上緣，不釘下緣。** 下緣是「↓ 最新」（`.jump-bottom`，右下 12px）與 composer 的地盤，
  那兩個是**動作**；提問是**參照**，蓋住動作的成本比蓋住舊訊息高得多。
- **夾三行（手機兩行），不是一行摘要也不是全文。** 一行截斷認不出是哪一題；全文則會讓一段
  長規格蓋掉半個對話區。三行足夠辨認，其餘交給展開。展開後給 `40vh`（手機 34vh）上限並
  自己捲，超長提問不會因為「展開」就吃掉整個畫面。
- **兩段點擊：展開 → 捲到那則。** 「展開」與「捲過去」都是這個浮窗該有的動作，但塞兩顆按鈕
  在一張 60px 高的卡片上太擠，而且對觸控來說整張卡當點擊區才好按。所以同一個點擊區分兩段，
  右上角用一句話說明下一段會做什麼（`點一下 · 展開全文` → `再點一下 · 捲到這則`）。
  短到沒被夾的提問沒有第一段，一點就直接捲過去——沒有東西可展開時不該假裝有。
  捲過去之後收回夾行狀態：人已經被送到訊息本身了，浮窗不必再佔三行以上。
- **捲過去要閃一下。** 停在一堆長得一樣的氣泡中間，不閃就不知道停在哪。用 `.msg.flash`
  在氣泡外圍打 1.6 秒的 accent 光暈；連按兩次時先把 class 拿掉再掛回去，動畫才會重播。
  這也是 `Bubble` 開始帶 `data-msg-id` 的原因——那是目前唯一能從清單外面指回某一則訊息的把手。
- **關閉只管這一回合。** 關掉的是「這一題我已經記得了」，不是「以後都不要」；下一個回合是
  另一題，值得再問一次（跟 `BlockedModal` 的 `dismissed` 同一個道理）。狀態綁在 turn id 上，
  換回合自動回到「夾行、沒關過」。
- **內容優先取這個回合自己的 user 訊息**，沒有（bot / team 起頭的回合）才退回整串最後一則。
  退回的那則仍然是「使用者最後說的話」，比什麼都不顯示有用。

## 2026-09-07 主機 shell（新增取捨）

- **主面板的一頁，不是 modal。** 這件事的動線是「開著它、一邊看輸出一邊下下一個指令」，而
  modal 蓋掉的正好是你想同時看的東西（側欄的主機清單、剛才那個 bot 的狀態）。所以它跟
  `TeamLaunchPanel` 一樣是主面板的一個分支，`shellView` 與 `selectedBotId` /
  `selectedProjectId` / `selectedTeamId` / `teamLaunch` 互斥，而且**排在最前面**：那是使用者
  剛剛按出來的視圖，比背景那個選取更該被看到。
- **入口留在「環境設定 → 主機」的每一列，按完就把彈窗收掉。** 開 shell 是「對這台主機做
  一件事」，跟重連、看 CLI 徽章、gh 登入是同一組動作，放在同一列最好找。但那張清單本身
  在彈窗裡，不收掉的話按完什麼都沒發生——新面板正好被蓋在後面。用的是 `Modal` 自己記載的
  關閉路徑（Escape），而不是另拉一條 store 狀態：彈窗的開關是 `Sidebar` 的本地狀態，
  模擬它自己的關閉動作才不會兩邊對不上。失敗時彈窗留著（原因與「重連」都在那一頁）。
- **按第二次「開 shell」是接回剛剛那個，不是再開一個。** 一台主機通常只需要一個 shell，
  而回來時想看的是上一個指令的輸出，不是一片空白。要「在某個目錄另開一個」才明確帶 `cwd`。
- **一行輸入 + 一排按鍵，不做整頁鍵盤接管。** `BlockedModal` 把每一顆鍵都轉給 pane，那是
  因為那裡在回答 TUI 的問題；shell 的主要動線是「打一行、按 Enter」，↑↓ 讓給指令歷史比讓
  給 pane 有用得多（那是這個面板唯一記得住的東西），Tab 也得留給瀏覽器走焦點。真的要按
  整片鍵盤的情境，按鍵列上的 `ctrl+c` / `Esc` / `Tab` / `↑` / `Enter` 就夠。
- **「清畫面」是真的送 `clear`，不是前端清 state。** 使用者要的是終端乾淨；把畫面上的字
  清掉只會在下一次輪詢（1 秒後）全部長回來，那比不做更糟。
- **兩種讀法，預設「畫面」。** `visible` 是「終端現在長什麼樣」，這是 shell 的常態；另一顆
  切到 `recent_unwrapped` ＋ 行數選單，看已經捲上去的輸出。herdr 對還沒捲過的 pane 這兩種
  `recent` 都回空字串（實測 2026-09-07），所以空的時候要**明講**「還沒有捲出畫面的內容」——
  一片空白看起來就是壞掉。
- **不記在 localStorage 的選取記憶裡。** `pane_id` 活不過 daemon 重啟，記住它只會在下次
  開啟時指向一個不存在的 shell。指令歷史記（每台主機一份、20 筆），那個換 daemon 也還有用。
- **「關閉」與「結束 shell」是兩顆。** 關閉只收畫面、shell 留著（回來接得回去）；結束才關
  pane，而且要二次確認——裡面可能正跑著東西，而畫面上的輸出關掉就沒了。

## 2026-09-07 已完成（未讀）（新增取捨）

回合的狀態多一段中間值：**進行中 → 已完成（未讀）→ 已完成（已讀）**。實作在
`web/src/store/unread.ts`（純函式 ＋ localStorage），store 只掛最小的 hook。

- **「完成」不等於「看到了」。** 一個 agent 跑完 8 分鐘的任務時，使用者八成正在看別的 bot、
  切到別的分頁、或人根本不在電腦前。舊的模型裡那一刻就直接變成「閒置」，燈號從黃轉綠，
  然後**什麼都不留下**——回來的人只看到一排綠燈，得一個一個點進去才知道誰講過話。中間這
  一段就是為了那個人留的。
- **「在看」是三件事同時成立：選的是它、分頁可見、視窗有 focus。** 少了最後一項，把瀏覽器
  丟在旁邊那台螢幕、人在別的 app 打字時進來的回覆會被當成已讀——那正是最需要留著徽章的
  情境。反過來，視窗回到前景時要主動把「現在開著的那個」標成已讀（`visibilitychange` /
  `focus`）：不然人就坐在畫面前面看著訊息，徽章卻還亮著，清除的時機永遠不會到。
- **燈號和徽章是兩件事，所以是兩個記號。** 燈號說的是**現在**在做什麼（working / idle /
  blocked），徽章說的是**你還沒看過**幾個回合。把未讀塞進燈號的顏色會兩邊都說不清楚：
  一個閒置但有未讀的 bot，燈要綠還是要亮？所以徽章是獨立的一顆，並排在燈號右邊，而且是
  **方角小標而不是圓丸**——同一列裡兩個圓點會被讀成兩顆燈。
- **`!` 前綴不是裝飾。** 側欄很窄，數字被截斷、被誤讀成模型參數（`4`、`5`）都發生過。
  `!2` 在任何寬度下都只可能是一件事。顏色用 accent（跟群組未讀同一家），不用 danger：
  未讀不是錯誤，只是還沒輪到你看。
- **數字是「回合」不是「訊息」。** 一個回合可能吐好幾則（續寫、工具輸出、hook）。使用者心裡
  的單位是「它回我幾次」，不是「資料庫多了幾列」。同一個 turn_id 只算一次；`message_added`
  與 `turn_updated`（終態）都算完成，去重表負責讓一個回合只跳一下。
- **專案收合就把底下的加總掛回標題。** 收合是「這一區我現在不想看」，不是「這一區的事我
  不想知道」。不加總的話，收合等於親手把徽章藏起來，那正好背叛了這個功能。
- **分頁標題的 `(N)` 只算 bot 那一邊。** 群組未讀跟 bot 未讀是**同一批回覆**的兩份帳
  （每則回覆同時記在它的 bot 和它專案的群組聊天上）；兩邊相加會把一則回覆數成兩個。
- **跨重整保留，但不動 daemon。** 未讀是「這個人看過什麼」，是瀏覽器這一端的事實，daemon
  不該知道，也沒有地方放。localStorage 存兩份：**已讀標記**（最後已讀的訊息 id + 時間，
  這是真相）和**數字**（快照）。只有標記的話重整後算不出數字——那時只有正在看的那個 bot
  會載入訊息，其他的一則都沒有；只有數字的話會跟真實訊息漂移。所以兩個都存，訊息真的載
  進來時再用標記重算一次校正。
- **刪掉的 bot 要把帳一起刪掉。** 不然 localStorage 只會長，而且那個數字會永遠加在分頁標題
  上——一個永遠點不掉的未讀。每次 `GET /api/state` 之後清一次。
